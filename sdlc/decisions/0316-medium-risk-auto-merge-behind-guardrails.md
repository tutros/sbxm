316. **Medium-risk PRs auto-merge behind guardrails, as an experiment (2026-11-10, the user's answers in #460's planning interview; extends [266], [280]):** track record from 2026-11-02 to 2026-11-10: 45 low-risk PRs auto-merged with 0 breaks (main's 4 red runs were 3 runner bus errors and the flaky test #468); the user merged 48 by hand (by their first review: 18 medium, 16 high, 14 low). (1) High risk stays the user's, with no trigger; only a new decision at a retro reopens it. (2) Before the first medium auto-merge: the review lists the checks it couldn't run and a non-empty list never arms (#545); the Pester tests of `scripts/` run in Windows CI (#546); an issue's required real check ([273]) is recorded on the PR before arming (#547); a veto window (#548); size S or M only and no `Cargo.lock` change (#549). A second reviewer (a different harness from the first; claude while codex reviews) and auto-revert come only when a break shows they're needed; until then [280]'s pause covers a break. (3) The veto window: 2 hours from the last clean review, announced by a Windows toast whose click opens the PR and by a PR comment saying when it will be armed; a `hold` label stops arming, a `go` label arms at once, neither arms when the window ends. Labels need repo write access, so GitHub authenticates the choice; no toast button merges directly. (4) Trial: 10 medium auto-merges (#550), judged at the first retro after the 10th. The first break after one (a red `main` or a fix it needed; runner faults and known flaky tests don't count) pauses medium auto-merge until the user decides. Measures: breaks of 10; how each was armed (`go` or the window's end) and how many were held; minutes from clean review to merge against the user's hand merges. Kept if 0 breaks in 10 and `hold` used at most twice.
