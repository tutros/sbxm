317. **The loop runs local and cloud tasks at once (2026-11-11, the user's answers in #561's planning interview; evidence from #390; uses [245], [258], [298], [299], [304], [309]):** this machine allows one local sandbox (16 GB), and cloud sandboxes use no local memory or disk, so the loop may run one local and several cloud tasks side by side. (1) **Evidence first ([258]):** #390 ran 2 cloud tasks at once by hand (#585, #586, 2026-11-11) next to a local loop task (#574): no provider usage limit with 3 Claude workers and 3 Codex reviews at once; setup 7m55s each against 6m10s alone (the extra time before the sandbox create); worker times 463 s and 553 s against 556 s alone; worker token cost $0.65 and $1.39 against $1.37 alone. 3 at once is not measured. (2) **Child processes:** the loop starts each task as its own `sbxm task run` process and supervises it (start, wait, finish); per-task locks, slots and `run.log` already work across processes, and a crashed task doesn't stop the loop. Not threads. (3) **Counts:** `[resources] cloud_slots = N` in `config.toml`, next to `sandbox_slots`, using [304]'s slot mechanism and account-wide: every command that creates cloud sandboxes takes one, by hand too. Unset means the loop runs no cloud tasks (today's behavior; opt-in). (4) **Routing:** the next issue in the usual order goes to the first free slot, local first (no extra cost), cloud when the local slot is busy; labels `run-local` and `run-cloud` pin an issue to one place. (5) **Host-side gates:** a task's host-tier gates take the local sandbox slot while they run, so a cloud task's host gates wait for a local worker; the slot is held for the gates only. (6) **Shared records:** one loop-log row per task, written when it ends (finish order), keeping its own start time, with a new "Slot" column (local or cloud); the 5-PR pause counts awaiting PRs plus running tasks, and no new task starts while their sum reaches 5; toasts are unchanged, one per event, each naming its issue. (7) **Resolves, check-run fixes and queue jobs ([298], [299], [309])** are child jobs like tasks, take slots by the same rules, and go ahead of new issues; never two jobs on the same PR at once. (8) **Finishing:** a short finish lock lets one finish (push, open the PR, arm auto-merge) run at a time; a PR that conflicts after another merges goes to (7)'s resolve. (9) **Side by side:** the existing **Related:** rule (`src/task/select.rs`) is the only guard; a related issue waits until its partner ends; no prediction of file overlap. (10) **Rate limits:** no new limit code; [245](d)'s usage-limit wait applies per task, and while any task waits out a provider's limit the loop starts no new task on that provider. A fixed per-provider cap waits for a trigger: the first usage limit hit while several tasks run. (11) **Cost:** `cloud_slots` is the only cap for now (it bounds concurrent cloud sandboxes, so spend per hour); `sbx` shows no sandbox cost. A money cap waits for a trigger: `sbx` shows cost, or a monthly bill above what the user expects. (12) **Stop and restart:** `task loop --stop` starts nothing new, lets running tasks finish through their PRs, then exits; Ctrl-C or a crash stops the children with the loop, and each task records itself interrupted as today; on restart the loop first resumes every interrupted task it owns, once each, then takes new issues.
