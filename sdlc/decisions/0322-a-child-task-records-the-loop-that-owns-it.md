322. **A child task records the loop that owns it (2026-11-12, the user's answer on issue #616, #612's review Q-1; amends [294](1) and [310](4); builds on [321](2)):** since #612 the loop runs a task's `task run` and `task resume` as child `sbxm` processes, so a child's `task.json` `process` names the child while the loop's lock names the loop, and matching a task to its loop by equal process no longer finds a loop's task. (1) **The loop gives each child its own identity** (pid and start time, as its lock records it) in the environment variable `SBXM_LOOP_PROCESS`, as JSON; the child records it in the tasks it takes as `loop: {pid, started_at}`, next to its real `process`, which stays the child's. A task run by hand has no `loop` field. The field follows `process`: a command that takes a task from another process writes its own loop, or drops the field when it has none (a command run by hand), and the process already recorded keeps it through its own writes (stage changes, a stage's end). (2) **`sbxm status` matches a running task to the loop by `loop` when it is present**, else by `process` as before ([294](1)), so a loop's child shows as its current task. (3) **The loop's restart recovery** ([310](4)) treats a task whose `loop` names the dead loop as owed one resume, as it does a task whose `process` is the dead loop; a task run by hand (no `loop`) is left alone, and one whose `loop` names another loop is not touched. (4) The equal-process rule stays for tasks without the field (records written before this change, and the loop's own steps such as `task finish`). `hooks.task_loop` keeps its one meaning (the loop finished this task, [294](1)) and is not reused for ownership.
