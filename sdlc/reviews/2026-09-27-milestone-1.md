## Must fix

**M1. A seed with a link is refused only after kits are written and validated.**
- Where: `src/commands/new.rs:104` (`seed::copy`, which runs `reject_links`) comes after `kit::write` (line 82) and
  `backend.validate_kit` (line 85).
- Evidence (probe): seed with a junction → the error is right, but `FakeBackend` recorded two calls
  (`validate …\kits\1150fd3b3e3c\common`, `validate …\harness-claude`) and `<base>/.sbxm/` exists afterwards.
- Why: decision 47 ("the seed is checked before anything is written"); check-before-acting convention. The existing
  test `seed_containing_a_link_is_an_error_and_copies_nothing` only asserts no create and no workspace.
- Fix: run the link check with the other seed checks (new.rs:54–72), before `check_secrets`; extend that test to
  assert `backend.log()` is empty and `.sbxm` doesn't exist.

**M2. `sbxm new` for a sandbox that already exists writes kits, then fails with `sbx`'s hint.**
- Where: `src/commands/new.rs` has no check for an existing sandbox before writing kits (line 82) and calling
  `create` (line 117).
- Evidence (real `sbx`, `sbxm new sbxm-it-review` twice): the second run printed `ERROR: sandbox
  'sbxm-sbxm-it-review-claude' already exists. Use 'sbx run --name sbxm-sbxm-it-review-claude' to connect to it`,
  then `Error: `sbx create` failed for sandbox sbxm-sbxm-it-review-claude (exit code: 1)`. With a changed config, the
  failed run also leaves a new `kits/<hash>/` folder behind.
- Why: check before acting; errors must say `<problem>; <fix>` with an sbxm command (`sbx run --name` skips sbxm's
  drift check, decision 31).
- Fix: before writing anything, if the project's state has an entry for this harness and `replace` is off, fail with
  `sandbox sbxm-demo-codex already exists; open it with `sbxm open demo --harness codex``. Test with `FakeBackend`:
  no calls, no new kit folder.

## Should fix

**S1. Instruction and managed-settings files can be read from outside the profile through a link.**
- Where: `src/config.rs:481–501` (`resolve_inside`) checks path components only; `read_instructions` and
  `read_managed_settings` follow links. `read_home_files` refuses links (line 532).
- Evidence (probe): `instructions.mandatory = "linked/mandatory.md"` where `linked` is a junction to a folder outside
  the profile → `new` succeeds and the kit's `CLAUDE.md` is `FROM OUTSIDE THE PROFILE`.
- Why: decision 62 (paths "must stay inside" the folder, so a profile is self-contained); inconsistent with the link
  rule for `home_files` (decision 63) and seeds (decision 47).
- Fix: after resolving, canonicalize the path and require it to start with the canonical folder; or refuse links
  as `home_files` does. One test each for instructions and managed settings.

**S2. The invalid-kit error always blames the profile's network entries.**
- Where: `src/commands/new.rs:91`.
- Evidence (probe): the bad host came from `.sbxm/demo/sandbox.toml`, but the message says `check the network entries
  in profile 'default' (…\profiles\default\profile.toml)` and doesn't mention `sandbox.toml`. The kit can also be
  invalid for reasons other than network entries.
- Fix: name the profile file and, when it exists, the project's `sandbox.toml`, without guessing the section.

**S3. `list`'s note for a sandbox without state has no fix.**
- Where: `src/commands/list.rs`, `note()`: `no sbxm state; not created by sbxm here`.
- Evidence: seen in the real run above for the user's own sandboxes, which were created under a *different*
  `base_dir`. The note gives no next step, and "not created by sbxm" is wrong in that case.
- Why: `<problem>; <fix>` convention (decision 48).
- Fix: e.g. `no sbxm state under this base_dir; remove it with `sbx rm <sandbox>` if it's stale`.

**S4. Several failure messages have no fix.**
- Where: `src/commands/doctor.rs` `validate_kits` (`generated kit {name} is invalid: …`) and the free-space error
  (`free space for base dir: …`); `src/commands/new.rs:62` (`seed … is not a directory`) and the bare `?` on
  `fs::canonicalize` at lines 64–65 (an OS error with no path or context).
- Why: `<problem>; <fix>` convention.
- Fix: add the fix to each (and context to the two `canonicalize` calls).

**S5. Harness names are repeated in `kit.rs`, and `list` re-implements `harness_flag`.**
- Where: `src/kit.rs:140–143` (`("sbxm-harness-codex", "codex")` …) and `196–199` (`"harness-codex"` …) repeat what
  `Harness::as_str` returns; `src/commands/list.rs` `note()` builds the `--harness` hint itself instead of using
  `commands::harness_flag`.
- Why: duplicated knowledge; adding a harness means editing three places in step. Simple-code rule: the same tests
  pass with the names derived from `as_str`.
- Fix: derive `sbxm-harness-{h}`, `harness-{h}` and the agent from `as_str` (make `Spec.name` a `String`); have
  `list` parse the harness and call `harness_flag`.

## Questions

**Q1. Should Pi sandboxes warn about the skills store, like Gemini?**
- Evidence: `src/harness.rs:74` warns for Gemini only; decision 46 says the store serves neither Gemini CLI nor Pi,
  and S7 saw no skills mount for Pi (empty store, so unproven). The test `pi_without_reference_instructions_doesnt_warn`
  asserts no warning for Pi with the default `readonly` store.
- Recommendation: yes, extend decision 72 to Pi.

**Q2. Should `home_files = "."` (or `""`) be refused?**
- Evidence (probe): `[harness.claude] home_files = "."` succeeds and copies the profile folder itself, including
  `profile.toml`, into the sandbox's home directory.
- Recommendation: refuse a path that resolves to the profile (or project) folder itself, with a message naming a
  subfolder to use instead.
