### M3S6-1 - A strict `pi` sandbox from a template can reach `registry.npmjs.org`, outside `[template].allow`

**Where:** `src/template.rs:315-327`, `src/commands/new.rs:113-114`, `src/template.rs:21-30`
**What happens:** this slice makes `new` create sandboxes from a template for every harness `check_supported`
accepts, and `pi` is one of them. `denied_hosts` returns an empty list for every harness but `codex`, and its doc
comment justifies that with "the other harnesses' kits allowing only their provider (decision 217, spike S15)".
Spike S15 says the opposite for Pi: `sdlc/spikes/S15-results.md` question 4 created a template sandbox with a narrow
kit (`allow: []`) and found "`registry.npmjs.org 200`" and "`sbx policy ls ... --wide`: one kit rule, allow tcp
`api.anthropic.com`, `platform.claude.com:443`, `registry.npmjs.org`". So a profile with `[template] strict = true,
allow = []` and `sbxm new demo --harness pi` (template built) gets a sandbox that reaches the npm registry: no
`--deny-network`, no post-create check (the check returns early on an empty deny list, `src/template.rs:337`), and
no warning. `only_a_strict_codex_sandbox_gets_deny_rules_and_the_check` (`tests/new_template.rs:665`) covers strict
`claude` and non-strict `codex` only; no test creates a strict `pi` sandbox.
**Why it matters:** decision 200(b) ("a sandbox of a strict profile ... gets only the profile's runtime allow list")
and decision 218 ("[200](b) stands"; a harness whose kit adds hosts gets strict templates only if those hosts can be
restricted, else it is refused before any sandbox is created). Criterion 1: a confirmed security promise is broken
silently, now that this slice creates strict sandboxes from templates.
**Fix:** follow [218]'s rule for `pi` as for `codex`. Until a bounded real-`sbx` check shows Pi still answers with
`--deny-network registry.npmjs.org` (the Pi kit runs an npm proxy step at startup, S15 question 3, so this is not
obvious), refuse a strict profile with the `pi` harness in `template::choose`, before any write, with a message that
names [218] and the host; record the choice as a new decision. If the check passes, generalize `denied_hosts` and
the post-create check to a per-harness table of extra kit hosts (`pi`: `registry.npmjs.org`) instead. Test first:
in `tests/new_template.rs`, a strict `pi` profile with a built template; assert the refusal (or the deny list and the
`network_rules` call) and that no sandbox was created. Correct the doc comment of `denied_hosts`.
**Size:** M: one refusal or a per-harness table, a real-`sbx` check for the deny variant, one decision, tests
**Depends on:** none known
**Related:** M3S6-2 (same function; fix together if the per-harness table is chosen)
**Acceptance criteria:**
- [x] `sbxm new <p> --harness pi` with a strict profile and a built template either is refused before any write
      (no create, no kit dir) or creates the sandbox with `--deny-network registry.npmjs.org` and checks its rules
- [x] A test covering it fails before the fix and passes after (`tests/new_template.rs`)
- [x] The `denied_hosts` doc comment no longer claims every non-`codex` kit allows only its provider
- [x] A new numbered decision in `sdlc/decisions.md` records the choice
- [x] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass
- [ ] Docs updated where behavior users see changed (README in slice 11), or "no user-visible change" -- not done: README and the code layout in slice 11
**Status:** fixed in 71f9f7c: strict `pi` refused before any write (decision 231, the user agreed 2026-10-19); the deny variant is issue #266. The `denied_hosts` doc comment was corrected in 2e2171d. Test: `a_strict_profile_is_refused_with_pi_before_any_write`, red before the fix.

### M3S6-2 - The post-create check is skipped for a strict `codex` sandbox whose allow list names all nine extra hosts

**Where:** `src/template.rs:332-340`, `src/commands/new.rs:171`
**What happens:** `check_codex_rules` returns `Ok(())` when `denied` is empty, and `denied` comes from
`denied_hosts`, which is empty when `[template].allow` lists all nine hosts of `CODEX_EXTRA_HOSTS`. The check is the
only guard against a newer `codex` kit adding a host (decision 221: "so a later `codex` kit that adds a host can't
widen a strict sandbox silently"), and it is skipped exactly then. Failing input: a strict profile with
`allow = ["github.com", "api.github.com", "codeload.github.com", "release-assets.githubusercontent.com",
"registry.npmjs.org", "download.docker.com", "archive.ubuntu.com", "security.ubuntu.com", "ports.ubuntu.com"]`, a
built `codex` template, and `FakeBackend::with_network_rules(codex_rules(&["telemetry.example.com:443"], &[]))`:
`new_codex` returns `Ok`, `network_rules` is never called, and `state.json` records the sandbox, which reaches
`telemetry.example.com`. (Read from the code; the test below confirms it.)
**Why it matters:** decision 221 (confirmed 2026-10-16): "after creation and before any agent command, sbxm reads the
kit rule's hosts ... and, if one is allowed that is neither an OpenAI host, in `[template].allow` nor denied, removes
the sandbox and refuses". The rule applies to every strict `codex` sandbox, not only to one with something denied.
Criterion 1 (contradicts a confirmed decision on a security guard) and 3 (no test or real check exercises this case).
**Fix:** decide whether to check by "strict `codex` sandbox from a template" (the same condition `denied_hosts`
uses), not by `denied.is_empty()`; for example a `template::strict_codex(&profile, harness, template)` predicate both
use, or pass the chosen template to `check_codex_rules`. Test first: the failing input above in
`tests/new_template.rs`, expecting the refusal naming `telemetry.example.com` and `rm sbxm-demo-codex` in the log.
**Size:** S: one condition in one module, one test
**Depends on:** none known
**Related:** M3S6-1 (same function), Q-1
**Acceptance criteria:**
- [x] With all nine hosts in `[template].allow` and a kit rule adding `telemetry.example.com:443`, `new --harness
      codex` calls `network_rules`, removes the sandbox, refuses naming the host, and writes no `state.json` entry
- [x] A test covering it fails before the fix and passes after (`tests/new_template.rs`)
- [x] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass
- [x] Docs: no user-visible change

### M3S6-3 - A failed rule read or removal leaves the strict `codex` sandbox behind, unrecorded and unexplained

**Where:** `src/template.rs:346`, `src/template.rs:363`
**What happens:** `check_codex_rules` runs after `backend.create`. If `backend.network_rules` fails (`sbx policy ls`
exits non-zero, or `parse_policy_ls` meets a rule without `name` or with an unknown `decision`), the `?` returns the
error without removing the sandbox: a strict sandbox whose rules were never checked stays in `sbx`, `state.json` has
no entry for it, and the message says only that `sbx policy ls` failed. The user's next `sbxm new` then fails at
`sbx create` (name taken) and `sbxm open` says "exists but sbxm has no state". Likewise, when an unexpected host is
found and `backend.remove` fails, the `?` drops the refusal: the user sees the `sbx rm` error, not which host was
found, and the sandbox with the extra host stays. No test covers either path (`FakeBackend::network_rules` never
fails).

(`<problem>; <fix>` naming the exact command). Should-fix: no agent runs through sbxm in the left sandbox (`open`
refuses it), but the cleanup and the explanation are lost.
**Fix:** on a `network_rules` error, remove the sandbox and refuse ("cannot read the network rules of S: ...; sbxm
removed it"); on a failed removal, keep the host in the message and name `sbx rm <sandbox>`. Test first with a
`FakeBackend` whose `network_rules` fails (a new `with_failing_network_rules`) and with `failing_remove()`.
**Size:** S: one function, a fake option, two tests
**Depends on:** M3S6-2 (same function)
**Acceptance criteria:**
- [ ] A failing `network_rules` on a strict `codex` create ends with `rm <sandbox>` in the log and an error that says

- [ ] A failing `remove` after an unexpected host gives an error naming the host and `sbx rm <sandbox>`

### M3S6-4 - `open`'s template hint can refuse `open` of a healthy install sandbox

**Where:** `src/commands/open.rs:79`, `src/template.rs:199-201`, `src/template.rs:240`
**What happens:** `open` calls `template::ready(&request, backend)?` for every install sandbox of a profile with
`[template]`. `ready` goes through `usable`, which propagates errors from `Record::load` (a template record that isn't
valid JSON), `backend.version()` and `backend.template_ls()`. Any of these makes `open` return the error before
`attach`, although the sandbox is unchanged and the hint is only advice. Failing input: a profile with `[template]`,
an install sandbox `sbxm-demo-claude` running, and `<base>/.sbxm/templates/default-claude.json` containing `{`:
`sbxm open demo` fails with "template record ... is not valid" instead of attaching.
**Why it matters:** decision 208: "`open` prints one hint naming `open --rebuild`; it does not refuse." Should-fix: the
error names its own fix, and the record has to be corrupt or `sbx template ls` failing.
**Fix:** treat an error from `ready` as "no hint" in `open` (optionally one warning line), so only the drift check
can refuse. Test first in `tests/new_template.rs`: the failing input above, `open` attaches.
**Size:** S: one call site, one test
**Depends on:** none known
**Acceptance criteria:**
- [ ] With an invalid template record, `sbxm open demo` on an unchanged install sandbox attaches (log ends with

## Questions

### Q-1 - Should the post-create check fail closed when it finds no `kit:<sandbox>` allow rule?

**Where:** `src/template.rs:350-360`, `src/backend/sbx.rs` (`parse_policy_ls`)
**What happens:** the check looks only at allow rules with `resource_type == "network"` named exactly
`kit:<sandbox>`. If `sbx policy ls` reports none (a later `sbx` renames the rule or the resource type, or sbxm's own
mixins end up in a differently named rule, which decision 221(c) lists as "Not tried"), the check finds nothing and
passes; `FakeBackend`'s default empty rule list shows this path is accepted today. Other allow rules scoped to the
sandbox are not checked at all. Decision 221(a) observed that a `codex` sandbox always has the kit rule, so its
absence means the output changed, which is the case the check exists for.
**Recommendation:** (a) refuse and remove the sandbox when no `kit:<sandbox>` allow rule is found, and check every
allow network rule whose scope is this sandbox against the same three sets (recommended: fails closed, small); or (b)
keep it as is and rely on end-to-end check 7. Size if (a): S.
**Size:** S
**Depends on:** M3S6-2
**Status:** answered (a) by the user 2026-10-19, decision 232; fixed in the commit after 71f9f7c (named in its
message): every allow rule scoped to the sandbox is checked, a missing kit rule removes and refuses, global rules
are left to the user. Tests: `a_strict_codex_sandbox_without_a_kit_rule_is_removed_and_refused`,
`another_allow_rule_scoped_to_the_sandbox_is_checked_too` (both red before the fix),
`a_global_allow_rule_is_left_to_the_user`.
