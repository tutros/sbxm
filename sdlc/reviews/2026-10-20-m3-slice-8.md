### M3S8-3 - A lock file at a PR's head is read into memory with no size limit

**Where:** `src/template.rs:171-180`, `src/template.rs:310`
**What happens:** `Locks::Commit::read` runs `git cat-file blob <commit>:<file>` through `git::run_bytes`, which
holds the whole blob in memory, then hashes it. At a PR's head, or at a worker's tip, that blob is written by
someone else. A multi-GB `Cargo.lock` is read whole before any refusal. Decision 198 caps a commit object at 1 MiB
(`rewrite::read_commit` calls `cat-file -s` first) for the same reason. The rest of the path is safe: the path comes
from sbxm's own template record, `rev:path` doesn't follow links in the tree, a tree or a missing file is an error
and reads as stale, and git runs hardened against `repo.git` only [159].
**Why it matters:** the slice is risky because this read takes untrusted input. Not must-fix: `check_pr_reviewable`
refuses forks, so the author can already push to the repo, and the harm is memory, not a widened sandbox.
**Fix:** `cat-file -s` first. A blob over a limit (for example 16 MiB, recorded as a decision) counts as "differs"
(stale), and the reason says it is too big.
**Size:** S: one function, one test.
**Depends on:** none known
**Acceptance criteria:**
- [ ] A PR head whose `Cargo.lock` is over the limit refuses a strict reviewer before its sandbox, naming the size, without reading the blob
- [ ] A test covering it fails before the fix and passes after (`tests/task_template.rs`)
- [ ] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass
- [ ] Docs updated where behavior users see changed, or "no user-visible change"

## Questions

### Q-1 - What should the strict refusal say when a task's own commits changed the lock file?

**Where:** `src/template.rs:233`, `src/template.rs:310-318`, `src/task/pipeline.rs:2878-2892`, `src/task/pipeline.rs:2396-2413`
**What happens:** (the author's point 1) an in-task reviewer refused at the delivered tip leaves the task
`reviewing (failed)` with the note `review round N: ...`, and the error is only the template's
`...stale: the lock files of commit <sha> (Cargo.lock) differ ...; rebuild it with `sbxm template build <p>
--harness codex --warm <repo>``. A PR task is left `gating (gates_failed)` with "could not start the review",
though no gate ran. Both can be continued: `task review --issue N` and `task resume --issue N` both accept
`reviewing/failed` (machine rows "retry the reviewer"; resume.rs's `(Reviewing, Failed)` arm goes to
`review_issue`), and `task review --pr N` accepts `gating/gates_failed`, re-running the gates. The worker's sandbox
is not remade, because it still exists. So the next command works once a usable template exists. But in the G1
case (the worker changed `Cargo.lock`, the test
`a_worker_that_changes_the_lock_file_keeps_its_sandbox_and_a_strict_reviewer_is_refused`) the hint's `<repo>` would
have to be a checkout of a branch that exists only in the task's `repo.git`. Warming from it also makes every new
worker from `main` stale. Neither message names the command to continue with.
**Recommendation:** keep the refusal and decision 216's `--warm` hint, and for a task add which commit to warm from
and the continue command: "...; or build it from that commit, then run `sbxm task review --issue N`". When the
commit is the task's own (not the base or a PR head), also say the lock change came from the task (gap G1) and that
`strict = false` lets its review install instead. Record it as a new decision, adding to [216]. Option b: leave the
message as it is until G1 is built.
**Size:** S: one message for task callers, two tests.
**Depends on:** none known
**Answer (2026-10-20):** the user chose the recommendation (a); decision 235.

### Q-2 - Is a resumed worker checked at the delivered tip instead of its starting commit, as decision 216 says?

**Where:** `src/task/pipeline.rs:1605-1622`
**What happens:** decision 216 says "issue and spec workers use their starting commit (a resumed worker the same
one) ... fix rounds the delivered branch's tip". `ensure_worker_sandbox` always uses the delivered branch's tip. The
two differ only when commits were collected before the resume: a `working (failed)` worker that still delivered
commits, or any `gating`/`reviewing`/`fixing`/`ready` resume. In the latter group the remade sandbox runs fix rounds,
so the tip is 216's own rule. For a `working (failed)` rerun with a changed lock file, a strict profile is refused
where 216 implies a check at the start commit.
**Recommendation:** keep the tip (the clone the sandbox mounts holds the tip's lock file, and a remade sandbox
serves the fix rounds as well), and record it as a new decision narrowing 216's "a resumed worker the same one".
Option b: use the recorded starting commit for `prepared` and `working` stages.
**Size:** S: a decision entry (option b: one branch and a test).
**Depends on:** none known
**Answer (2026-10-20):** the user chose the tip; decision 234.

## Verification and checklist notes

- Plan row 8: worker (issue, spec, continued PR), in-task reviewer, `task review --pr` and `task resume`'s remade
  worker all go through `plan_sandbox` + `SandboxPlan::create`. Fix rounds run in the worker's sandbox and create
  nothing, so they are covered by the remade worker at the tip. `task.json`'s `worker.template` and
  `reviewer.template` are set before `create`. The lock check reads `repo.git` through hardened git, never the
  agent's clone [159]. Required tests are present: `a_pr_head_that_changes_the_lock_file_refuses_a_strict_reviewer_before_its_sandbox`
  (base still matches) and the G1 test. Tests read as written first (each commit carries its tests); not run here.
- Author's point 2 (`ensure_worker_sandbox` rewrites `config_hash`): right, and it hides no drift by itself.
  `check_config_drift` runs first and hashes the profile as it is now, under the variant the record names
  (template variant when `worker.template` is set). Any profile edit, `strict` toggled, `[template].allow` changed
  for a template sandbox or `[template]` removed is refused before the rewrite. The new hash is the current
  profile's under the variant actually created, which is what the next drift check needs. Two caveats: the write
  (M3S8-2), and the profile being loaded twice (drift check, then `plan_sandbox`), so an edit between the two loads
  is recorded instead of refused (a window of milliseconds, nit). A switch from the install variant to the template
  variant on remake is a new sandbox from the current profile, like `open --rebuild` [208].
- Author's point 3 (`prepare_pr` passes `None`): consistent with 216. Those kits only validate early and give the
  PR record a `config_hash`. The reviewer sandbox is made later by `open_review_workspace`, which checks the
  lock files at the fetched head and builds the variant it creates. No code reads a PR task's `config_hash` (it
  has no worker, so `check_config_drift` never runs), so the install-variant hash there is only a label (nit).
- Refusals before a sandbox: every strict refusal comes from `plan_sandbox` before `create` and before the
  reviewer record is written. Worker refusals clean up the task folders (tested).
- Nits: a refusal that doesn't need the lock (no template, stale build hash, old `sbx`) and the kit validation now
  come after `clone_bare` in `prepare`/`prepare_spec_resolved`, a network clone wasted per refused target in a
  `task run` list. `Locks::hash(...).ok()` turns an unreadable `repo.git` into "differ from the ones it was warmed
  with". A PR task's strict refusal is recorded as `gates_failed` although no gate ran (as for any
  `open_review_workspace` failure before). `README.md` and the `AGENTS.md` code layout don't mention task templates
  yet (slice 11).
