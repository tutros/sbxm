### M-1 - Unsupported harnesses bypass the recorded template refusal

**Where:** `src/template.rs:288`, `src/template.rs:325`, `src/template.rs:351`
**What happens:** `choose` checks only whether `[template]` exists and whether strict Pi is in use; it never calls `check_supported`. For Antigravity or Gemini, `usable` therefore reaches its missing-record branch and proposes ``sbxm template build <profile> --harness <h>``. `template build` rejects that exact command at `src/template.rs:26-33`. A strict profile is refused with a fix that cannot work; a non-strict profile warns and creates an install sandbox instead of refusing the unsupported template harness.
**Why it matters:** decision 204 and the milestone goal explicitly say Antigravity and Gemini are refused with “templates are not supported for this harness yet.” This is wrong behavior now and contradicts a confirmed decision (must-fix criterion 1).
**Fix:** make `choose` reject an opted-in profile on an unsupported harness before `usable` or any write/backend mutation, using `check_supported`'s message. Keep the separate strict-Pi refusal.
**Size:** S: one shared chooser branch and command-level tests.
**Depends on:** none known
**Acceptance criteria:**
- [ ] A strict `[template]` profile with Antigravity or Gemini is refused before any write and names the unsupported harness, without suggesting `template build`.
- [ ] A non-strict `[template]` profile with Antigravity or Gemini is likewise refused, as decision 204 requires, rather than falling back to installs.
- [ ] Tests through template-using create paths fail before the fix and pass after it.

### M-2 - `config show` reports a hash and kits different from the recorded template sandbox

**Where:** `src/config.rs:108`, `src/commands/config_show.rs:42`
**What happens:** this change introduces install and template hash variants and makes `new`, `open`, and `list` select the recorded variant. `config show`, however, still unconditionally calls `config_hash`, renders `hash_input_toml` for the install variant, and emits `kit::all`. Thus `sbxm config show <project> --harness <h> [--kits]` for a template-backed sandbox prints neither the hash in `state.json` nor the kits applied to that sandbox. The focused test `a_template_sandbox_hashes_the_runtime_allow_list_and_an_install_one_does_not` passes and proves the two hashes differ.
**Why it matters:** decisions 65, 208, and 230 promise that `config show` explains the hash `open` compares for the recorded sandbox. The command now returns a wrong diagnostic result (must-fix criterion 1).
**Fix:** retain the selected state entry while resolving a project, choose the recorded variant from its `template` field, and render both the matching hash input and matching kit variant. Preserve the existing preview semantics when there is no recorded sandbox.
**Size:** S: one command, a variant-aware hash renderer, and tests.
**Depends on:** none known
**Acceptance criteria:**
- [ ] For a recorded template sandbox, `config show <project>` prints the exact `state.json` hash, includes `[template].allow` in the rendered input, and `--kits` omits profile install steps while using the runtime allow list.
- [ ] For a recorded install sandbox, existing hash and kit output is unchanged.
- [ ] Tests covering both variants fail before the fix and pass after it.
- [ ] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass.
- [ ] README's “prints exactly what's hashed” statement needs no qualification after the fix.

### S-5 - `doctor` underreports disk used by retained previous templates

**Where:** `src/commands/doctor.rs:227`, `src/commands/template_ls.rs:61`
**What happens:** when a rebuild keeps an old tag because a sandbox or task uses it, the record stores it in `previous` and `sbx template ls` still reports its size. `doctor` nevertheless adds only `record.size_bytes` and counts only records, so one record with a current 2 GiB image and an in-use previous 2 GiB image is reported as “1 template, 2 GiB in total” instead of the roughly 4 GiB actually consumed. `template ls` only appends `(+1 previous)` to the current image's size.
**Why it matters:** decision 205(c) adds this total specifically to make template disk use visible on the drive that has run out before. The current total is misleading precisely while cleanup is intentionally deferred.
**Fix:** use the already-loaded backend image list to include every current and previous recorded tag in the count and total, while keeping missing-image warnings explicit.
**Size:** S: one report calculation and tests.
**Depends on:** none known
**Acceptance criteria:**
- [ ] A record with one present previous image reports two owned images and the sum of both backend-reported sizes.
- [ ] Missing previous images are not counted as disk use; the total is based on present recorded images.
- [ ] A test fails before the fix and passes after it.
- [ ] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass.

### Q-1 - Needs a decision: Should a warm template build report step progress?

**Where:** `src/commands/template_build.rs:541`
**What happens:** `warm_up` runs each configured or built-in command through `run_sandbox_tier` without writing progress. The end-to-end build emitted nothing during a 283-second warm-up, so it was indistinguishable from a hung command until completion.
**Recommendation:** print one line before each warm-up step and one completion line, without streaming command output; this gives bounded progress while preserving current error-tail behavior. Option B is to document that warm-up is silent and make no code change.
**Size:** S: progress writes and output tests.
**Depends on:** none known

### Q-2 - Needs a decision: Should `run.json` record the selected template tag?

**Where:** `src/run/results.rs:106`, `src/run/kits.rs:31`
**What happens:** each run harness entry records its profile, config hash, and kit paths but not `HarnessKits.template`. Rebuilding a template creates a fresh tag and can freeze a different agent version, yet two otherwise identical runs have indistinguishable identities in `run.json`.
**Recommendation:** add a nullable `template` field to each `harnesses[]` entry so saved results identify the image actually selected. Option B is to keep `run.json` stable and accept that provenance gap; decision 206 currently requires template tags only in `state.json` and `task.json`.
**Size:** S: additive run-result fields and tests.
**Depends on:** none known
