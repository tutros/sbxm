### M-1 - A wildcard runtime allow entry is silently overridden for strict Codex sandboxes

**Where:** `src/template.rs:455`, `src/template.rs:467`, `src/template.rs:514`
**What happens:** the profile syntax already documents wildcard hosts (`README.md:218` uses `"*.githubusercontent.com"`), and decision 202 makes `[template].allow` the same runtime network allow list for a template sandbox. For a strict Codex profile with `allow = ["*.githubusercontent.com"]`, `release-assets.githubusercontent.com` is covered by that entry, but `denied_hosts` tests only string equality at line 467. It therefore adds `--deny-network release-assets.githubusercontent.com`, which wins over the baked allow rule. The post-create check repeats the exact-equality test at line 519. The configured wildcard is silently ineffective for this built-in Codex host; no test covers a wildcard in `[template].allow`.
**Why it matters:** this silently drops a configured setting, contrary to decision 11 and decisions 202/221. It meets must-fix criterion 1: the sandbox's observable egress contradicts its runtime allow list.
**Fix:** use one host-pattern matcher, with the wildcard semantics accepted by the kit network list, in both `denied_hosts` and `check_codex_rules`; keep exact-host matching as a special case.
**Size:** S: one shared matcher and focused strict-Codex tests.
**Depends on:** none known
**Acceptance criteria:**
- [ ] A strict Codex profile with `[template].allow = ["*.githubusercontent.com"]` does not add `release-assets.githubusercontent.com` to `CreateSpec.deny_network`.
- [ ] The post-create rule check accepts `release-assets.githubusercontent.com:443` under that wildcard and still rejects an unrelated host.
- [ ] Tests covering both results fail before the fix and pass after.

### Q-1 - Needs a decision: should removal protect a running comparison run?

**Where:** `src/template.rs:102`, `src/run/results.rs:84`, `src/commands/template_rm.rs:49`
**What happens:** template users are discovered only from `state.json` and `task.json`. A comparison with several sequential repeat waves can run for hours without either record. `template rm`, or the previous-tag retirement after a rebuild, can therefore remove its chosen tag between waves; the next wave's `sbx create -t <tag> --pull never` fails. Decision 233 accepts the seconds-long equivalent race for `new`, but no decision covers a whole run.
**Why it matters:** protecting active runs requires extending a persistent format and the deletion guard, which is the user's decision rather than a review fix.
**Recommendation:** accept and document the race for now, and log a gap triggered by a real run wave failing after concurrent template removal. Option A (recommended) keeps this milestone smaller. Option B records the tag in `run.json` (S-7) and has `users` treat every run without `completed_at` as in use; that gives stronger protection but expands the run state contract and needs interrupted-run cleanup semantics.
**Size:** S for option A; M for option B because it changes the removal guard and run-state lifecycle.
**Depends on:** option B depends on S-7.
