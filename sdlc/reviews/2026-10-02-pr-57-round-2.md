### R2-M1 - Running only one gate tier lets review skip the other required tier

**Where:** `src/task/pipeline.rs:694-712`, `src/task/pipeline.rs:1135-1145`
**What happens:** `task gates --tier sandbox` runs only the sandbox list, but `finish_gating` records the task as `gating/passed` whenever that selected subset passes. `review_issue` treats every `gating/passed` record as proof that gates are current and skips `Tiers::ALL`. A focused regression test with one sandbox gate and one host gate failed:

```text
$ cargo test --test task_review_flow a_partial_gate_run_does_not_authorize_review_without_the_other_tier -- --exact
assertion failed: review must run the configured host gate omitted by the partial on-demand run
  left: 0
 right: 1
```

The inverse path is also allowed: `--tier host` starts with `sandbox_ok = true`, so it runs agent-written code on the host without first passing the configured sandbox tier.
**Why it matters:** decision 160 and spec §7 require the host tier only after the sandbox tier passes, and decision 152 requires the configured gates before review. This produces a wrong authorization result and bypasses a confirmed safety boundary, so it meets must-fix criterion 1.
**Fix:** distinguish a complete successful gate phase from a selected-tier diagnostic run. Before review, skip gates only when the latest phase proves that every configured tier ran and passed; do not let `--tier host` run unless the sandbox tier passed for the same collected revision.
**Depends on:** none known
**Acceptance criteria:**
- [ ] With both tiers configured, `task gates --tier sandbox` followed by `task review` runs the host tier before creating the reviewer; `--tier host` without a current sandbox pass is refused or runs the sandbox tier first.
- [ ] A regression test covering each partial-tier sequence fails before the fix and passes after.
- [ ] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass.
- [ ] README and `sdlc/spec-m2b.md` describe whether a selected-tier run is diagnostic or authorizes later stages.

### R2-M2 - A timed-out host gate leaves its child processes running on Unix

**Where:** `src/task/gates.rs:217-250`
**What happens:** off Windows, `kill_tree` calls only `child.kill()` on the `sh` process. A child that keeps running survives the reported timeout; because it retains the output pipes, both drain threads wait for EOF and the three-second `recv_timeout` returns an empty output tail. The process behavior reproduces on this review host with the same parent-only kill:

```text
$ sh -c 'sleep 30 & wait' & ...; kill -9 <shell-pid>; ...
child <pid> survived after shell <pid> was killed
```

The surviving process had to be killed separately.
**Why it matters:** spec §7 promises a per-command timeout, and `ShellHostRunner`'s own contract says a command that outlives it is killed together with what it started. Here agent-written code continues on the host after sbxm reports it stopped, which is a security and resource-leak risk and meets must-fix criterion 1.
**Fix:** start Unix host gates in their own process group/session and kill the group on timeout. Keep captured output in storage readable even when a descendant still holds a pipe, rather than publishing it only at EOF.
**Depends on:** none known
**Acceptance criteria:**
- [ ] On Unix, a gate that starts a long-lived child and waits times out with both shell and child gone; its pre-timeout output remains in `gates.log`.
- [ ] A regression test covering the surviving-child case fails before the fix and passes after; retain the Windows process-tree coverage too.
- [ ] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass.
- [ ] No user-visible docs change is needed unless timeout wording changes.

### R2-S1 - Concurrent gate commands can both pass the in-memory guard and overwrite one task record

**Where:** `src/commands/task_gates.rs:63-73`, `src/task/record.rs:304-322`, `src/task/record.rs:407-414`
**What happens:** each process independently reads the same non-running `task.json` and passes `check_can_gate`; `begin_gating` checks only that process's in-memory copy. Both then use the same sandbox, `<id>-gates` checkout, `gates.log`, `task.json.tmp`, and final `task.json`. One run can delete the other's checkout, and the last rename loses the other run's stage, notes, and gate results. The earlier slice-7 review recorded this as G7-4, and no lock was added afterward.
**Why it matters:** decision 144 makes task commands blocking and `task.json` is the durable lifecycle record. A normal second invocation must refuse instead of corrupting that record or reporting gates for mixed runs.
**Fix:** acquire an exclusive per-task mutation lock before re-reading and changing the record, with stale-lock recovery tied to the recorded pid/start time. Hold it through gate checkout cleanup and the final record write.
**Depends on:** none known
**Acceptance criteria:**
- [ ] Two gate invocations released simultaneously for one task result in exactly one run and one clear refusal; `task.json` and `gates.log` contain one coherent phase.
- [ ] A deterministic barrier-based concurrency test fails before the fix and passes after.
- [ ] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass.

### R2-S4 - Finish cannot recover when the PR exists but its URL was not recorded

**Where:** `src/task/finish.rs:473-500`, `sdlc/spec-m2b.md:137`
**What happens:** finish pushes first and calls `pr_create`; every creation error leaves the task `ready` with a retry note. If GitHub created the PR but the response was lost, or someone opened the same head/base PR after the push, every retry calls `pr_create` again and gets the existing-PR refusal, so the task never reaches `finished` and never records the URL. There is no backend operation that looks up a PR by head branch. This remains the slice-10 review's should-fix 5.
**Why it matters:** the spec names an existing PR as a finish precondition/result, and the durable task record is meant to survive exactly this kind of partial external success.
**Fix:** add a `GitHubBackend` lookup for an open PR matching repo/head/base. Check it before creation and after an ambiguous create failure; adopt its URL only when all three fields match the task.
**Depends on:** none known
**Acceptance criteria:**
- [ ] When PR creation succeeds remotely but returns an error locally, the next `task finish` finds the matching PR, records its URL, and ends `finished` without creating or updating another PR.
- [ ] Fake-GitHub tests for adoption and mismatched head/base fail before the fix and pass after.

### R2-Q1 - Should the exact spec keep claiming every role flag is shared by start, review, and run?

**Where:** `sdlc/spec-m2b.md:141-142`, `src/cli.rs:161-288`, `README.md:70-77`
**What happens:** the spec says all worker and reviewer harness/model/time flags are shared by all three commands. The shipped CLI instead exposes worker flags on `start`, reviewer plus fix-time flags on `review`, and both sets on `run`; `cargo run -- task start --help` has no reviewer flags and `task review --help` has no worker flags. README documents the phase-specific surface, and the record—not a review-time flag—correctly chooses the worker for a fix round.
**Why it matters:** decision 143 delegates exact flags to the spec, so the contract and implementation disagree even though the phase-specific CLI is simpler and avoids accepted-but-unused flags.
**Recommendation:** amend spec §4 to list phase-specific flags as README does. Alternative: add every stated flag to every command and define what start records for a future reviewer and what review may override for an already-recorded worker; that adds state and behavior with no demonstrated need.
**Depends on:** none known
