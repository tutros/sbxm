## Must fix

### M3S9-1 - A pair only the judge uses gets a lock check, which decision 237 says the judge never gets

**Where:** `src/run/preflight.rs:97-123`, `src/run/kits.rs:67-88`, `src/template.rs:336-350`
**What happens:** `kits::pairs` puts the judge's (run profile, judge harness) pair in the list like any other, and
preflight runs `template::choose` on it with `Locks::Dir(seed)` or `Locks::Unseeded`. When no contestant shares that
pair, the lock check is the judge's own. Scenario: profile `default` is strict with a cold `claude` template and a
warm `codex` template; the run has two `claude` contestants, a `codex` judge and no `task.seed`. Preflight reaches
the `(default, codex)` pair, `usable` hashes `Locks::Unseeded`, which errors, so the warm template counts as stale,
and the run is refused: "the template of profile 'default' for codex is stale: the lock files of a run without a
seed (Cargo.lock) differ ...". With a non-strict profile the judge silently installs instead and the user gets a
warning about "the run's codex sandboxes". The same happens with a seed whose `Cargo.lock` differs from the codex
template's, though the judge's workspace holds only `judge-prompt.md`.
**Why it matters:** decision 237: "The judge follows its pair's choice: it builds nothing, so it gets no lock check
of its own." Criterion 1: a strict run is refused (or a judge installs) against a confirmed decision. No test has a
judge-only pair: all three judge cases share `claude` with the contestants.
**Fix:** for a pair no contestant uses, call `choose` with a lock source that always matches (e.g. a
`Locks::Skip`/`judge_only` flag in `Request` that skips the warm comparison), and keep `Unseeded`/`Dir(seed)` for
pairs a contestant uses. `pairs` (or preflight) needs to know which pairs are judge-only.
**Size:** S: one flag through preflight and `usable`, one test.
**Depends on:** none known
**Acceptance criteria:**
- [x] A strict run with a warm template used only by the judge and no seed creates the judge from that template (`CreateSpec.template` is the tag), with no warning
- [x] The same with a seed whose `Cargo.lock` differs from the judge's warm template
- [x] A pair shared by a contestant and the judge still gets the seed's lock check (existing tests stay green)
- [x] The new test fails with the flag removed (both failed before the fix: "the template of profile 'default' for codex is stale")
- [ ] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass
- [ ] Docs updated where behavior users see changed, or "no user-visible change"

### M3S9-2 - A run without a seed is told to rebuild the warm template, which can never make it usable

**Where:** `src/template.rs:204`, `src/template.rs:214`, `src/template.rs:336-350`
**What happens:** for `Locks::Unseeded` the stale reason and fix come from the generic lock-mismatch arm. A strict
profile with a warm `claude` template and a run with no `task.seed` is refused with: "the template of profile
'default' for claude is stale: the lock files of a run without a seed (Cargo.lock) differ from the ones it was
warmed with (a run without a seed has no lock files); rebuild it with `sbxm template build default --warm <repo>`".
Following the hint builds another warm template, and the next run is refused the same way: no warm template can
match a run without lock files (decision 237). The fixes that work are setting `task.seed` in the run-config,
building the template cold (`sbxm template build default`, which replaces the warm one for every user of the
profile, decision 205(a)), or `strict = false`. The non-strict warning carries the same wrong hint in its
parentheses. `a_run_without_a_seed_warns_once_and_installs_with_a_warm_template` only checks for "a run without a
seed".
**Why it matters:** the review bar: a message is must-fix when it "sends the user to a wrong action" (criterion 1;
decision 201: the message names the exact command that fixes it).
**Fix:** a reason and fix of their own for `Locks::Unseeded` in `usable`, e.g. "the template of profile 'default'
for claude is warm, and a run without a seed has no lock files to check it against; set task.seed in the
run-config, or build the template without --warm".
**Size:** S: one branch in `usable`, two test assertions.
**Depends on:** none known
**Acceptance criteria:**
- [x] The strict refusal for an unseeded run with a warm template names `task.seed` and a cold build, not `--warm <repo>`
- [x] The non-strict warning says the same in its parentheses
- [x] Tests assert both and fail with the old wording (`a_strict_run_without_a_seed_and_a_warm_template_names_a_fix_that_works`, `a_run_without_a_seed_warns_once_and_installs_with_a_warm_template`)
- [ ] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass
- [ ] Docs updated where behavior users see changed, or "no user-visible change"

### M3S9-4 - `run.json` doesn't record which template the run's sandboxes came from

**Where:** `src/run/results.rs:106-111`, `src/config.rs:482-499`
**What happens:** each `harnesses` entry records `profile`, `harness`, `config_hash` and `kits`, but not
`HarnessKits.template` or `deny_network`. `template_config_hash` doesn't include the tag either. Two runs of the same
config before and after `sbxm template build` (a new tag, a new Claude Code version frozen in it, decision 203(c))

**Why it matters:** a run's results are its record (decisions 28, 55, 128), and decision 206 records the template
for every other sandbox kind (`state.json`, `task.json`). Not must-fix: adding a field later is cheap, and
`config_hash` already tells template from install.
**Fix:** `"template": h.template` in each `harnesses` entry, with a test in `tests/run_template.rs`.
**Size:** S: one field, one assertion.
**Depends on:** none known
**Acceptance criteria:**
- [ ] `run.json`'s `harnesses` entry for a template pair has its tag, and `null` for an install pair
- [ ] A test asserts both and fails without the field

## Questions

### Q-1 - Should `template rm` and a rebuild see a running `sbxm run`?

`template::users` (`src/template.rs:102-121`) reads `state.json` and every `task.json` only. A run with `repeat = 3`
creates sandboxes in sequential waves over possibly hours; a `sbxm template build` of the same profile and harness
during it removes the old tag as unused (decision 205(a)), and every pair of the next wave fails at `create`.
Decision 233 accepted the same race for `new` because its window is seconds; a run's window is the whole run. No
decision covers runs. **Recommendation:** accept it for now and log a gap with the trigger "a run's wave fails
because its template was removed"; if wanted later, `users` can list runs whose `run.json` has no `completed_at`
and names the tag (which needs M3S9-4 first).
