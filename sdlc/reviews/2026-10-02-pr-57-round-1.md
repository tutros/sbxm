## Must fix

### R1-M1 - A worker can make reviewer or fix setup overwrite files outside its clone

**Where:** `src/task/pipeline.rs:1337`, `src/task/pipeline.rs:1524`
**What happens:** The worker controls its clone and every committed path that reaches the reviewer's clean checkout. `run_fix_round` and `open_review_workspace` nevertheless call `fs::create_dir_all` on that clone's `.sbxm-task` and then `fs::write` fixed child names without checking for links. A worker can replace `.sbxm-task`, `review.md`, `fix-prompt.md`, `issue.md`, or `prompt.md` with a symlink; the host follows it when writing the review or prompt, so a relative target such as the task metadata directory can be overwritten. The protected reader in `repo::read_agent_file` performs the missing canonical/plain-file checks, but these write paths do not.
**Why it matters:** This is a host-file overwrite through agent-controlled repository content, so it is a security and data-loss defect (must-fix criterion 1). It breaks the trust-boundary intent of decision 159 and the repository convention that untrusted paths and links are revalidated before use.
**Fix:** Before writing sbxm-owned files, make `.sbxm-task` a verified real directory inside the expected clone. In a fresh reviewer checkout, safely remove any tracked `.sbxm-task` path and recreate it; in the worker clone, refuse a linked directory or linked destination file before the fix round writes anything.
**Depends on:** none known
**Acceptance criteria:**
- [ ] A worker commit containing `.sbxm-task/prompt.md` as a symlink cannot change its target during reviewer setup, and a linked fix-round destination is likewise refused without changing its target.
- [ ] Tests covering reviewer setup and fix-round setup with linked `.sbxm-task` paths fail before the fix and pass after.
- [ ] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass.
- [ ] No user-visible docs change is needed unless the refusal adds a documented recovery step.

### R1-M2 - A worker harness override is forgotten before review and the fix round uses the wrong adapter

**Where:** `src/commands/task_run.rs:97`, `src/commands/task_review.rs:80`, `src/task/pipeline.rs:1305`
**What happens:** `task run --worker-harness codex` applies the override only to the `task_start::Options` at lines 97-109. `task_review::run` then reloads `sbxm-task.toml` and only applies reviewer/time/profile flags; it never reconciles `config.worker` with `task.json`. `run_fix_round` takes the sandbox name from the recorded worker but passes `env.config.worker.harness` and model to `headless::run`. With the default file (`worker = claude`) and a Codex start override, a must-fix review therefore runs the Claude command adapter inside the recorded Codex sandbox. The reviewer's default is also recomputed against the file's Claude worker, so it can silently choose Codex to review the actual Codex worker, contrary to the different-harness default. The focused existing fix-round test passes because it uses the file defaults and does not exercise an override.
**Why it matters:** This produces the wrong command in the one fix round and silently defeats independent-review decision 148; it contradicts decisions 139 and 149 and spec section 5.2 (must-fix criterion 1). The PR description says the real fix round was not exercised, so later manual verification will not catch this before merge (criterion 3).
**Fix:** For an issue review, load the recorded worker harness/model from `task.json` into the effective config before choosing the default reviewer or running a fix. Make `task run` preflight and carry one effective worker/reviewer configuration through both phases; in particular, reject a missing reviewer secret before starting the worker.
**Depends on:** none known
**Acceptance criteria:**
- [ ] `task run --worker-harness codex` with no explicit reviewer uses a non-Codex reviewer, and a must-fix finding runs the fix command with the Codex adapter/model in the recorded Codex sandbox.
- [ ] A test for the overridden-worker fix round fails before the fix and passes after; a missing reviewer secret in `task run` is also refused before any sandbox is created.
- [ ] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass.
- [ ] README flag/default descriptions remain accurate.

### R1-M3 - On-demand gates can approve manual edits that review and finish never receive

**Where:** `src/commands/task_start.rs:337`, `src/commands/task_gates.rs:63`, `src/task/pipeline.rs:1520`
**What happens:** After a gate failure, `task start` tells the user to fix the worker's clone and run `task gates`. That command opens the record and calls `run_gates`; it never creates, verifies, or fetches a new bundle. The sandbox tier therefore sees the manual clone edits, while the host tier and every reviewer clone still come from the older `repo.git` branch. If the sandbox tier passes (and the host tier is off or the stale commit also passes), the task advances and review/finish inspect or publish the pre-fix commits. README line 72 even documents that the two tiers see different states without warning that review and finish remain stale.
**Why it matters:** A task can be marked gate-passed, reviewed, and published without the change the user just validated. That is wrong behavior under decisions 152 and 159 and spec sections 5.2, 6, and 7 (must-fix criterion 1).
**Fix:** Before on-demand gates run after a failed gate, collect the current committed worker branch through the same fixed in-sandbox bundle command and verified host fetch used after worker/fix runs (or remove the manual-fix instruction and provide a different supported recovery that updates `repo.git`).
**Depends on:** none known
**Acceptance criteria:**
- [ ] After a failed gate, a new commit made in the worker clone is present in `repo.git` before on-demand gates pass, and the subsequent reviewer clone contains that commit.
- [ ] A test that commits a manual gate fix fails before the fix and passes after, asserting both sandbox gates and reviewer/finish use the same commit.
- [ ] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass.
- [ ] README describes the supported gate-failure recovery without claiming two tiers may validate different revisions.

### R1-M4 - An interrupted reviewer setup can leave a sandbox that task rm cannot name

**Where:** `src/task/pipeline.rs:1558`
**What happens:** Reviewer setup calls `backend.create` at lines 1558-1568 and only stores `record.reviewer.sandbox` and writes `task.json` afterward at lines 1569-1576. If sbxm is killed while the multi-minute create is in progress, the record is already `reviewing/running` but has no reviewer name. `task rm` obtains sandbox names only from the record; for a PR task there is not even a worker sandbox to fall back to, so the created reviewer sandbox is left behind. Worker setup deliberately writes its agent record before `backend.create` at lines 485-509 to solve the same slice-13 problem.
**Why it matters:** This contradicts decisions 145 and 153 (the durable record precedes work and stores sandbox names), and it can leak a real sandbox after interruption (must-fix criteria 1 and 3).
**Fix:** Populate and atomically write the reviewer agent, including its sandbox name, before calling `backend.create`; retain the existing cleanup and failed-stage handling if creation returns an error.
**Depends on:** none known
**Related:** R1-M1, because both fixes touch reviewer workspace setup but are otherwise independent.
**Acceptance criteria:**
- [ ] At the start of a reviewer `create` call, `task.json` already names that reviewer sandbox, and an interrupted task's removal plan includes it.
- [ ] A create-hook/interruption test fails before the fix and passes after for both issue and PR review tasks.
- [ ] `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass.
- [ ] No user-visible docs change is needed.
