4. **Commits after the last review merge unreviewed** (2 instances): #304's merge of `main` and #311's 2041ec0 (the

5. **Windows CI is the floor of the merge wait and its flakes cost reruns** (2 reruns, #302 and #303, both causes

## Decision 245: assessment input (the loop trial)

The trial is decision 245(h)'s "3 days or 15 tasks"; it reached 15 tasks in one day, 14:59 to 20:40.

- **Outcomes:** 15 of 15 clean in round 1 (0 must-fix, 0 should-fix, 0 fix rounds, 0 repeat findings, 0 draft PRs);
  15 PRs merged the same day; 1 hand commit (#304's conflict merge, which decision 245(e) says to report rather than
  resolve; whether the user asked for it isn't recorded).
- **Time:** 5m31s to 13m15s to ready (median 8m03s); 2.6 tasks an hour over the span, but the machine ran tasks 37%
  of it. The rest: waiting for the user 1h57m48s (the cap and the empty queue), the S14 spike 46m12s, the loop's own
  steps 46m28s (median 3m24s a gap).
- **Stops:** 1 refusal before any write (#222, ours: a stale `PR: #n` line); 0 environment stops, so decision
  245(d)'s triage (disk, `sbx`, usage limit, killed process, flaky gate, resume once) and the work-stop path (draft PR)
  were never exercised; no overnight stretch.
- **Interventions:** none during tasks; the user answered the queue report, added the allow rules and merged 15 PRs
  (median 29m12s open to merge). The session made 3 mistakes (issue bodies, one answer against decision 135, "ready
  to merge" before CI), each turned into a rule.

**Recommendation:** don't design `sbxm task loop` from this trial yet. What it measured is the happy path of small
issues; what a feature would have to automate (stop triage, resume, draft PRs, overnight limits) didn't happen once,
and the measured bottleneck is the user's queue and merges, which a feature wouldn't shorten. Run a second window
with a deeper queue that includes M issues and an overnight stretch, then decide (proposal 1).

## Proposals

At most three, ranked by the time they would save.

### 1. A full queue before a loop window

- **Problem:** waiting for the user was 56% of the loop's idle time: the empty queue after task 1 (53m57s, only #291 was
  labeled) and the cap of 5 PRs awaiting merge (1h03m51s); open to merge took a median 29m12s.
- **Change** (decision 245's way of working, the loop's start): "Before a loop window starts, label at least as many
  issues as the window's task count (including M issues where any are decided), and agree a merge time with the user
  so the cap of 5 isn't reached while the user is away."
- **Measure:** the share of the loop's idle time spent waiting for the user (this window: 56%, 1h57m48s), and tasks per
  hour of the span (2.6).
- **Trial:** the next loop window (decision 245's second window).
- **Cost:** answering the open points of more issues in one sitting up front; no new process, it moves existing work
  earlier.
- **Recommendation:** adopt; it is also the way to get the M issues and stops the 245 assessment still lacks.
- **Decided 2026-10-23: adopted** (decision 249; amends decision 245's loop start).

### 2. Check an issue body before labeling it `ready-for-worker`

- **Problem:** the loop's only friction came from the session's own issue text (4 instances in #222, #272, #273).
- **Change** (decision 245(b), the labeling step): "Before adding `ready-for-worker`, read the issue back with `gh
  issue view` and check three things: no `PR: #n` line names a merged or closed PR, the body keeps its line breaks
  (bodies are written with the Write tool and `--body-file`), and every recorded answer agrees with the decisions it
  touches."
- **Measure:** labeled issues needing a body fix or refused before any write (this window: 3 of 15).
- **Trial:** the next 15 labeled issues.
- **Cost:** a minute per issue; adds a small check, and the 2026-10-23 handoff lessons already ask for two of the
  three parts, so this mostly writes them down where the loop reads them.
- **Recommendation:** adopt.
- **Decided 2026-10-23: adopted** (decision 250; amends decision 245(b)'s labeling step).

### 3. Self-review hand-made PRs before the independent review

- **Problem:** 3 of 3 hand-made or hand-fixed PRs (#289, #292, #311) needed a fix round after their first review
  (2 must-fix, 1 question, 22m48s to 16h of gaps), against 0 of 15 worker PRs, which run the worker self-review of
  decision 188; and 2 last commits merged unreviewed (#304, #311).
- **Change** (`sdlc-code-review` or `AGENTS.md`'s workflow): "A PR made in the session goes through the worker's
  self-review checklist (decision 188) before `task review --pr N`; a commit pushed after the last review gets a
  narrow re-review or is named in the PR as unreviewed."
- **Measure:** hand-made PRs with a must-fix or a question in review round 1 (this window: 3 of 3), and commits merged
  after the last review (2).
- **Trial:** the next three hand-made PRs.
- **Cost:** a few minutes per hand-made PR; adds process, and the comparison with worker PRs is weak (different kinds
  of work), so this is the least certain of the three.
- **Recommendation:** try it, low priority; drop it if the first three still need a round.
- **Decided 2026-10-23: adopted** (decision 251; `AGENTS.md`, "Workflow").

## Experiment verdicts

Proposed, not asked separately: keep 242 for milestone 4, keep 243 (it worked as a measure; the loop's idle time
between tasks, which it misses, is measured alongside it here), keep 244 and judge it again on an M or L limit change. Decision 245's assessment (feature or not) is still to do with the user; this retro recommends making
it after a second loop window run under decision 249.
