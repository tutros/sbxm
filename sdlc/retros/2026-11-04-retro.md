## Patterns (each with at least two instances)

1. **A fix round fixes the instance, not the kind.** Tasks that needed a second fix round: 4 of the 9 with a review
   fix round (#313, #317, #320, #384). Repeat must-fix: #317 (the fix checked the scope's SHA but not the whole range
   token) and #320 (a continued hand-opened PR still counted as loop-opened) were partial fixes of the same kind;
   #384's two were correct hand-backs (decision 272) that the loop still counted as repeats. Every fix round is a
   fresh session that re-reads the code and the review; nothing of the builder's reasoning carries over.
2. **Small changes pay the whole pipeline.** #365 (+1/-1), #369 (+4/-2), #357 (+2), #417 (+25/-6), and the S issues
   filed from should-fix items (#353, #361, #374, #407, #409) each got their own worker, review and PR: about 15-20
   minutes to `ready` and 20-30 more to merge, each. Decision 164's counts (below) show no sign that a finer split
   lowered findings.
3. **Our own rules collide.** On 2026-11-04: `task finish` refusing workflow files forced hand pushes (#412, #415);
   the strict warm template refused a branch whose `Cargo.lock` was behind (filed #402); `task resume` refused after
   a resources change (#410). Decisions 275-284 added ten rules in five days; one planned rule was dropped (decision
   283's hard stop) and none was removed.
4. **Linux passes, Windows fails.** PR #400's `mklink /J` paths failed only on the Windows CI job (hand fix 25005f9);
   #407's lock race showed as a Windows flake on PR #394's run. The CI caught both; the sandbox gates (Linux) can't.
5. **Disk stops in the loop**, 4 of 6 tasks in loop window 2 (#325, #324, #345, #341): fixed in code by PR #378 and
   PR #397, no instance since.

## Proposals

At most three, ranked by the rework they would save. All three come from the 2026-11-04 agenda on #351.

### 1. Fix rounds go back to the builder's own session

- **Problem:** pattern 1. 4 of 9 tasks with a fix round needed a second one (#313, #317, #320, #384); 2 repeat
  must-fix were partial fixes of the same kind (#317, #320). The fix-the-kind rule (decision 188) asks for it in the
  prompt; a fresh session has to rebuild the builder's reasoning from the code.
- **Change:** a code issue (size M: keep the Claude worker's session file when the worker sandbox is released, copy it
  into the fix round's sandbox, and add `--resume <session>` to the fix round's command; Claude workers only, other
  harnesses unchanged), then a trial with it switched on. A blind replay of past fix rounds isn't possible: the
  archives keep no worker transcripts.
- **Measure:** tasks needing a second fix round (this window 4 of 9), repeat must-fix (4 in 3 of 10 tasks), and the
  fix round's cost in `task.json` (not compared before: only the latest run is kept).
- **Trial:** the next three tasks with a fix round.
- **Cost:** the code issue, and a resumed session carries a longer context (cost per fix round may rise). It adds no
  process step.

### 2. One worker for a group of related issues

- **Problem:** pattern 2. Small, related changes each pay a worker, a review and a PR. Decision 164's counts show no
  sign that a finer split lowers findings.
- **Change:** run #402, #403 and #404 (the unattended blockers, which share the branch-changed stop and are already to
  be done one after the other) as one spec task with all three issues' acceptance checks, one review loop and one PR.
  If it goes well, #375 and #376 (loop parts 2 and 3) next. Text for `sdlc-issue-flow`, "Ready the issue": "Issues
  that touch the same code and are to be done in order go to one worker as one spec, with every issue's acceptance
  checks; the PR closes all of them."
- **Measure:** hours from start to merged and review rounds for the group, against the window's M tasks (median 43.5
  min to first `ready`, median 1 round, 1 PR each); round-1 must-fix per 1,000 changed lines (window: 16 in 22 tasks).
- **Trial:** the next two groups (#402-#404, then #375-#376).
- **Cost:** a bigger PR to review, and a group stops together if one part blocks. It removes process (two PRs and two
  review loops per group).

### 3. Each retro removes one rule; this time, AGENTS.md's code layout

- **Problem:** pattern 3. Ten rules added in five days, none removed; three collided on one day. AGENTS.md is 50 KB,
  and its "Code layout" section is 31 KB of it, loaded by every session and every worker; it restates the code.
- **Change:** add to `sdlc-retro` section 4: "Every retro also proposes removing one rule or harness component: name
  the assumption it encodes, test it on the current models, and delete it if the numbers hold." This retro's
  candidate: replace "Code layout" with five lines (where the modules are, `docs/project.md` for the map, the Windows
  cargo warning, the Bash backslash hook), keeping the hook text verbatim. Assumption tested: agents need a prose map
  to find code.
- **Measure:** worker time to first `ready` (window median 20.5 min) and round-1 must-fix per task (16 in 22, 0.73),
  over the next three tasks; put the section back if both get worse.
- **Trial:** the next three tasks.
- **Cost:** none in process; agents may search more at the start of a task.

## Directions (recorded, not experiments)

- Issues state the goal, an acceptance check and the hard constraints; the mechanism is left to the worker unless it
  needs a fact or a product choice the worker can't make (#407's answer fixed "5 attempts, 50 ms").
- A verifier stage with real tools at our edges (Windows, real `sbx`, the cloud), failures fed back as a fix round
  (pattern 4).
- Review effort scaled by risk: low risk and docs one round, medium and high full rounds plus the verifier.
- Effort scaling across models: a cheaper model for docs-only work (first data point: #417's Sonnet worker, 1 must-fix
  then clean), a stronger one for L issues.
- **Model router (the user's goal):** `sbxm run` comparisons should rate models so a router can pick one per task.
  The data it needs, per run: the task's kind (code fix, feature, docs, review) and size, the harness and the
  resolved model id, gates passed, round-1 must-fix, rounds to `ready`, wall time, tokens and cost, and later an
  escaped-defect flag. Today `task.json` records `model: null` when the default is used and keeps only the latest
  run's usage, so task history can't feed a router yet.
