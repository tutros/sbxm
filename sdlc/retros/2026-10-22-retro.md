## Proposals

At most three, ranked by the rework they would save.

### 1. No parked should-fix findings at a milestone review

- **Problem:** should-fix findings from slice reviews are parked on the milestone branch and come back at the
  milestone review, some as must-fix: M2b (4, window 1), milestone 3 (10, 3 as must-fix, window 3). Filed as
  issues between tasks they don't come back (window 2).
- **Change** (`sdlc-implementation`, rule 8): "A slice review's should-fix findings are fixed in the next slice
  or filed as an issue before the milestone review starts, and the milestone PR lists each filed one with its
  issue number, so the review doesn't raise it again."
- **Measure:** findings at the milestone review that an earlier slice review raised (M3: 10) and milestone review
  rounds (M3: 3).
- **Trial:** the next milestone.
- **Cost:** a few fixes moved earlier; a list in the milestone PR. Adds a little process, removes a review round.
- **Decided 2026-10-22: adopted** for the next milestone (decision 242; `sdlc-implementation` rule 8, step 3).

### 2. Make the stop-to-next-command time visible

- **Problem:** the first-retro agenda asked for it; all three windows have it as unknown, while #202 (window 2)
  used 2h16m of machine time over 14.5 h, and #233 waited 79 min for disk.
- **Change** (`sdlc-retro`, the gather table): add the row "Time from each stop to the next command: the gap between
  a `run.log` line that ends a command and the next header, per task, with the stop's cause".
- **Measure:** its own value, first counted in the next retro; the target is to find the largest cause.
- **Trial:** the next retro.
- **Cost:** a few minutes per retro; no code.
- **Decided 2026-10-22: adopted** (decision 243; `sdlc-retro` section 2, the gather table).

### 3. A boundary change gets its boundary tests first

- **Problem:** the longest loops of windows 2 and 3 were boundaries: a limit, a size cap, a drive or path identity
  (#244, #258, #285, and #202's failure paths in window 2). Each fix round patched the value it was shown, and the
  next round found the neighbouring one. The edge-case checklist asks about failure paths, not limits.
- **Change** (the edge-case checklist answered at an issue's "Decided" step): replace it with one question, "Does this change have a limit, a size, or an identity (path, drive, ref) that decides
  behavior? Then the issue lists the boundary cases (at the limit, one over, one under, the largest input), and the
  worker writes those tests first."
- **Measure:** round-1 must-fix and rounds for issues that answer yes (window 3: #244 7 rounds, #258 5, #285 4).
- **Trial:** the next three issues that answer yes.
- **Cost:** one question per issue, a few test cases per yes; replaces the checklist rather than adding to it.
- **Decided 2026-10-22: adopted** (decision 244; `AGENTS.md`, "No open questions go to a worker").
