# Spike S17: can network rules be removed from a running cloud sandbox?

Issue #310, milestone 4 planning. Run 2026-10-23, about 23:45 UTC, hands-on in the main session, `sbx` v0.46.0,
`--cloud`. Everything is observed unless marked **inferred**.

**Verdict:** PASS. A running cloud sandbox's allow rules can be removed or replaced by deny rules, the change takes
effect at once, and that holds for the agent's own built-in hosts too. Answer 4 B of the planning (decision 255)
holds; its fallback A (refuse strict profiles in the cloud) is not needed.

## Question

A strict profile in the cloud has no template to start from (cloud templates are later, decision 254), so its
install steps run at create with the build allow list. Answer 4 B keeps strict mode by removing the build hosts from
the sandbox's cloud policy before the worker starts, then checking `policy ls` shows only the runtime list, like
decision 232. That only works if rules can be removed from a sandbox that is already running, and if the removal
applies to traffic at once.

## How it ran

One throwaway `shell` sandbox, `sbxm-spike-s17`, on the default shape, with `--ttl 1h --on-timeout delete`, and one
kit allowing two test hosts, `example.com` and `postman-echo.com`. About 5 minutes in all. The sandbox was removed at
the end.

## What was observed

1. `sbx --cloud create --name sbxm-spike-s17 --ttl 1h --on-timeout delete --kit <kit> shell`: created in 5 s
   ("configure 2 kit(s)").
2. `policy ls`: deny-all, the kit's two hosts, and the `shell` agent's own built-in list: `api.anthropic.com`,
   `claude.ai`, `console.anthropic.com`, `api.github.com`, `copilot.github.com`, `github.com`,
   `raw.githubusercontent.com`, 4 `googleapis` hosts, `api.mistral.ai`, 2 `nebius` hosts, `api.openai.com`,
   `openai.com`, `openrouter.ai`, `api.x.ai`.
3. Before any change: `example.com` answered 200, `postman-echo.com` 302.
4. `sbx --cloud policy rm network --sandbox sbxm-spike-s17 --resource example.com -f`: "Removed from allow", exit 0,
   and the output prints the new list.
5. `sbx --cloud policy deny network --sandbox sbxm-spike-s17 postman-echo.com`: "Added to deny ... Replaced allow
   rule(s)", exit 0.
6. On the running sandbox right after: `example.com` and `postman-echo.com` both failed with `curl` exit 7
   (connection refused). `api.openai.com` was still reached (421).
7. A host from the agent's built-in kit: `policy rm ... --resource api.x.ai` removed it, and `curl` then gave exit 7.
8. `--sandbox` takes the sandbox's name. The output of `rm` and `deny` prints the resulting list, so sbxm can parse
   it for its check.
9. Cleanup: the global policy was unchanged (deny-all, no rules); the sandbox was removed and `sbx --cloud ls` was
   empty.

## What it means for the design

- Strict mode in the cloud works as answer 4 B describes [255]: create with the build allow list so the install
  steps can run, then remove (or deny) every host outside the runtime list, then check the list.
- Built-in hosts can be removed in the cloud. Locally the `codex` kit's rule is `editable: false` and only a deny
  rule closes its hosts [221]; in the cloud a plain `policy rm` worked on a built-in host (`api.x.ai`). Whether every
  built-in host of every agent behaves the same way is **inferred** from one host of one agent.
- Even a `shell` sandbox's built-in list reaches many providers' hosts. The rule list a strict check reads must be
  the sandbox's whole list, not only the profile kit's hosts.
- `rm` and `deny` both print the new list, so the check after the removal can read it from their output or from a
  fresh `policy ls`. Which form sbxm uses is a plan choice (`sdlc/milestone-4.md`).
- Removal took effect on the running sandbox without a restart. Whether a rule removed this way comes back after a
  stop and start was **not tried**.
- Cost: one default-shape sandbox for about 5 minutes.
