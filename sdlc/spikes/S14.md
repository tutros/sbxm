# Spike S14: sbxm's sandboxes on Docker Cloud Sandboxes

Issue #245. Run 2026-10-23, 17:45-21:00 UTC, hands-on in the main session between loop tasks (decision 247), `sbx`
v0.46.0 (`991967dc`), Windows host; Q1 rerun with both kits 22:05 UTC after the PR 311 review. Everything is observed unless marked **inferred**. Spend: $0.79 of the $10 cap, the final reading after every spike sandbox was gone.

**Verdict:** works. All four must-pass questions pass (Q1 egress, Q2 secrets, Q3 timeout, Q4 repo in and bundle
out), Q7 says Codex reviews can run in the cloud on the user's subscription, and a full build and test of this repo
takes 5m37s on the large shape. Moving sbxm there changes how a sandbox is configured (flags instead of kits on a
template, secrets scoped by name before create, root setup only at create), so it is a milestone of its own
(decision 248), not a backend swap.

## How it ran

The planning answers are decision 247. Every spike sandbox had `--ttl 1h --on-timeout delete` and was removed after
its question; nothing was left in the cloud except the two OAuth secrets and one 260 MiB template, kept for the
milestone's planning (decision 248). Kits were written by hand in sbxm's `common`-kit format
(`schemaVersion: '2'`, `kind: mixin`).

## Q1: does sbxm's kit apply the network allow list, and does default-deny hold? PASS

- The account's default cloud policy is `deny-all` with no rules.
- First run, `common` only: `sbx --cloud create --name sbxm-spike-s14-q1 --kit <common kit allowing example.com>
  claude`: created in 8 s. The CLI returns an id (`sbx_...`), not the name.
- Rerun with sbxm's two kits in its order (decision 62; PR 311 review M-1), 22:05 UTC:
  `sbx --cloud create --name sbxm-spike-s14-q1b --ttl 1h --on-timeout delete --kit <common> --kit <harness-claude>
  claude`. `harness-claude` was written in the shape `src/kit.rs`'s `harness()` produces: `requires.agent: claude`,
  a mandatory `files/home/.claude/CLAUDE.md`, and the managed-settings step as `user: '0'`. Created in 9 s
  ("configure 3 kit(s)": the two plus claude's own). Policy: deny-all plus the claude kit's hosts and `example.com`;
  `example.com` 200, `www.wikipedia.org` blocked (`curl` exit 7, connection refused); `SBXM_PROFILE` set;
  `~/.claude/CLAUDE.md` holds the kit's text; `/etc/claude-code/managed-settings.json` holds the kit's JSON (the root
  step ran). Removed.
- `sbx --cloud policy ls <id>`: deny-all plus the claude kit's own hosts and the spike kit's `example.com`. The kit's
  allow list becomes the sandbox's cloud policy rules.
- `example.com` 200, `api.anthropic.com` reached (404), `www.wikipedia.org` blocked: `curl` exit 6, "Could not
  resolve host", over https and http. The kit's environment variables apply.
- **Differs from local:** a denied host failed at DNS in the first run (`curl` exit 6) and with connection refused in
  the rerun (exit 7), not with the local proxy's 403, and no `HTTP(S)_PROXY` variable is set (only `NO_PROXY`). Yet
  in Q5 a build script's HTTPS download from a host not allowed failed with `CONNECT proxy failed: proxy server
  responded 403`. Three shapes of refusal; why each appears is **not explained**. sbxm's real-`sbx` egress test
  (expects 403) needs a cloud variant that accepts all three.

## Q2: does a cloud secret reach the agent without its value entering the sandbox? PASS

Part 1, a fake value:
- `sbx --cloud secret set-custom` differs from local: `--host` takes exact DNS names only; the value must be literal
  (`--command` is refused as "local-only", so there is no host helper or refresh in the cloud); the proxy **sets a
  header** (`--header`, `--format`, default `Authorization: Bearer %s`) instead of swapping a placeholder; `--sandbox`
  takes the sandbox **name** (the `sbx_...` id is refused).
- A secret scoped to a sandbox that already existed did not reach it. Removed and created again under the same name:
  the env var holds only the placeholder (`sbx-cs-...`), the value is in no env var and no file (`grep -r /` without
  `/proc` and `/sys`), and an echo service on the allowed host received the header with the value. **Secrets attach
  at create:** store them before `create`.
- Cleaned up (`secret rm <service> --sandbox <name> -f`).

Part 2, the user's Claude login:
- The user ran `sbx secret set anthropic --oauth --cloud` (browser sign-in): stored at global scope, only in the cloud.
- A cloud `claude` sandbox, created in 9 s: `timeout -v --kill-after=10 120 claude -p '...' --output-format json`
  answered in 3.2 s with the same JSON and usage fields sbxm parses locally.
- Inside: `SBX_CRED_ANTHROPIC_MODE=oauth`, no token in the environment. A search for `sk-ant-` tokens matched one
  string, in a 34 MB runtime binary dated two days before the secret existed: a built-in 58-character placeholder,
  not the user's token. No leak.

## Q3: does the in-sandbox timeout behave as locally? PASS, with a note

- `timeout -v --kill-after=5 3 sleep 60`: exit 124 in 4.2 s, the `timeout:` line on stderr, nothing left running.
- A command that ignores TERM: exit 137 in 9.1 s, TERM then KILL lines.
- A shell that ignores TERM and leaves a child (`sh -c 'trap "" TERM; sleep 60'`): the TERM and KILL lines arrive,
  then `error: RunExecSession: stream error: sbxcloud: API unreachable interact stream closed before the process
  exited`, exit 1, after about 41 s (twice). The orphaned `sleep 60` keeps running.
- The same command in a **local** sandbox: exit 137 after 48.7 s, and the orphan also keeps running. The orphan is
  not cloud-specific (`timeout` kills only its direct child); the cloud difference is exit 1 plus a stream error
  instead of 137.
- sbxm recognizes a timeout by `timeout -v`'s stderr line (`headless.rs`), so this still classifies; a cloud backend
  must not read that stream error as "`sbx` unavailable" (`ExecUnavailable`) once the timeout lines were seen.

## Q4: can a repo go in and a verified bundle come out, with no host git in a sandbox-written folder? PASS

- The host bundled a host-owned one-commit repo; `sbx --cloud cp <file> <id>:/tmp/in.bundle` took 1.0 s. Inside
  (git is installed): clone from the bundle, one commit, `git bundle create /tmp/out.bundle <baseline>..HEAD`.
  `sbx --cloud cp <id>:/tmp/out.bundle <file>` took 1.1 s.
- On the host, in a fresh bare repo holding the baseline, with `GIT_CONFIG_NOSYSTEM=1`: `git bundle verify` okay, and
  the fetch puts the agent's commit on top of the baseline (decisions 159, 161).
- There is no workspace mount, so a cloud task's clone step becomes "bundle in, clone inside"; the bundle-out path
  works unchanged through `cp`.

## Q5: time and cost. Measured

- Large shape (8 vCPU, 15 GiB, a 30 GB root overlay) with a kit doing `sbxm-dev`'s install steps (apt
  `build-essential pkg-config libssl-dev` as root, rustup as `agent`): created and ready in **24 s** (locally the same
  setup is about 57 s plus the create).
- Full `cargo build --tests --locked`: **233 s**; `cargo test --locked`: **103 s**, every suite passing (rustc 1.99.1;
  the profile pins 1.93.0, which passed too when checking PR #304 on the same sandbox, except the flaky test of #307). Disk after one build: 20 of
  30 GB.
- Spend: $0.06 after Q1, Q3 and Q4; $0.13 after Q2, Q7 and Q6; $0.69 after Q5, whose large sandbox ran about 54 min
  (most of it checking PR #304), so roughly $0.56 for that hour (**inferred** from the two readings); $0.79 at the end, after the 9-second Q1 rerun. That $0.10 step is more than a 9-second default sandbox would suggest: late billing of the large sandbox or a minimum charge per sandbox are possible, but the split is **not known**.
- Found on the way:
  - `exec` can't run as root (`--user` is refused with `--cloud`). Root setup only happens through a kit's install
    step at create, which runs as uid 0. A step **without** `user:` also ran as root (rustup landed outside
    `/home/agent`): sbxm must write `user: agent` explicitly.
  - The image's own startup `apt-get update` holds the apt lists lock, which `DPkg::Lock::Timeout` doesn't cover;
    a retry loop on "Could not get lock" works.
  - `/tmp` is a tmpfs of half the RAM (7.9 GB here); a cargo target folder filled it. Workspaces go under `$HOME`.
  - A full disk made `ld` die with a bus error, and a filter that only listed failing suites printed nothing: count
    the passing suites instead.
  - The first `rm -f` of the large sandbox failed ("temporarily unavailable; retry the delete"); the retry worked.
    Cloud removal needs a retry.
  - Network rules can be added to a running sandbox: `sbx --cloud policy allow network --sandbox <name> <hosts>`.

## Q6: cloud templates. PASS, with a design change

- From a `shell` sandbox with Rust installed: `sbx --cloud template save <id> <name>` took 22 s (260 MiB, disk capture
  mode); a create from it took 11 s, with Rust and a marker file present.
- `create -t <template> --kit <dir>` is **refused** in the cloud: "--kit cannot be combined with --template; the kit
  defines the base image". Milestone 3 relies on exactly that combination locally. A cloud template sandbox gets its
  configuration from flags: `--allow-network`/`--deny-network`, `-e`, and secrets scoped by name.
- With flags: the policy is deny-all plus only the flags' hosts (the template's source sandbox rules don't carry
  over); the env applies.
- `-t` also refuses `--cpus`/`--memory`: a template's size is baked in when it is saved, so a template serves one
  shape.

## Q7: Codex in the cloud on the user's OpenAI login. PASS

- `sbx secret set --help` documents `--oauth` with `--cloud` for `openai` and `anthropic`. The user ran
  `sbx secret set openai --oauth --cloud`.
- A cloud `codex` sandbox, created in 8 s: sbxm's adapter form (`echo | timeout ... codex exec --json
  --skip-git-repo-check "..."`) answered in 3.1 s with the usual JSON events and usage.
- Inside: `~/.codex/auth.json` is `{"OPENAI_API_KEY": "proxy-managed"}`; a text-file search of `/home`, `/root`,
  `/etc`, `/tmp` and `/run` for JWTs, `sk-proj-` keys and `access/refresh/id_token` values found nothing outside a
  cloned plugin repo of examples. No leak.
- **Global cloud secrets attach to every cloud sandbox:** the codex sandbox also had `SBX_CRED_ANTHROPIC_MODE=oauth`.
  sbxm should scope each secret to its sandbox's name before create, so a sandbox only gets its own provider.

## For the milestone's planning

The facts above that change sbxm's design, in one list: no kit with a template; a template is one shape; no root
`exec`; secrets attach at create, by name, literal values only, header-set; global secrets reach every sandbox; three
shapes of egress refusal; the timeout's stream error; `/tmp` is small; removal needs a retry; no workspace mount.
