# Spike S8: GitHub access from a sandbox

**Status:** written 2026-09-27, not run. The repo owner doesn't plan to give workers GitHub access, so Q1–Q2 (no token
needed) can run any time, and Q3–Q4 wait for someone, e.g. a fork's owner, who meets the precondition below. **Output:**
fill in `sdlc/spikes/S8-results.md` (template provided). Nothing else.

## Why

Issue workers (`scripts/issue-workers.ps1`, decisions 80–82) have no GitHub access: the agent commits locally and the
host pushes. With GitHub egress and a `github` secret, the agent could read its issue, push its branch, open the PR
and tick acceptance criteria itself. This spike checks whether that works through `sbx`'s proxy, which domains it
needs, and whether these limits hold:
1. A fine-grained token scoped to one repo (contents, issues, pull requests; no workflows, no admin).
2. Branch protection on `main` requiring review, so the agent can open PRs but not merge them.
3. Egress limited to the few GitHub hosts the work needs.

The results feed a README section on turning this on (optional, per fork), and possibly a switch in the script.

Read first: decisions 30, 48, 58, 80–83 in `sdlc/decisions.md`; "Security model" in `README.md`; `scripts/issue-workers.ps1`.

## Precondition for Q3–Q4 (a human, before the run)

The worker never creates tokens, stores secrets or changes GitHub settings. Before the run, the human:
1. Creates a scratch repo `<owner>/sbxm-spike-s8` (not the real project) with a README on `main` and one open issue
   (#1), and protects `main`: pull request with 1 approving review required, no bypass for admins.
2. Creates a fine-grained token for that repo only: Contents read/write, Issues read/write, Pull requests read/write,
   Metadata read; **no** Workflows, no Administration. Expiry: 1 day.
3. Stores it in their own terminal: `sbx secret set github` (global scope).
4. Writes `<owner>` into the results header.

If `sbx secret ls` shows no global `github` service secret at the start, run Q1–Q2 only and mark Q3–Q4 **Blocked
("no github secret stored")**.

## Environment facts (verified 2026-09-27 unless marked)

- `sbx` v0.43.0 on Windows 10. `sbx secret ls` held only a global `anthropic` service secret. `sbx secret set --help`
  lists `github` among the service secrets. Secrets are global by default, and `--sandbox <name>` scopes one to a
  single sandbox. `--command 'gh auth token'` resolves the value on the host at use time.
- The Claude image (`docker/sandbox-templates:claude-code-docker`, Ubuntu 26.04) has `gh` 2.46.0 and `git`. With no
  `github` secret stored, the environment still has `GH_TOKEN` (value not inspected), plus `HTTPS_PROXY` and
  `PROXY_CA_CERT_B64`. The global git config sets `safe.directory` for the workspace and has no credential helper.
- sbxm's secrets check counts only global service secrets (decision 58). A sandbox-scoped secret can't be named in
  `secrets.services`.
- Workspaces on `C:` fail (decision 56). Use only `E:\sbxm-it\spike-s8\`.
- sbxm with a separate config: set `SBXM_CONFIG_DIR=E:\sbxm-it\spike-s8\config`, holding a `config.toml` with
  `base_dir = 'E:\sbxm-it\spike-s8\projects'` and `profiles_dir = 'E:\sbxm-it\spike-s8\config\profiles'`. The real
  sbxm config is never touched.
- `sbx policy log <sandbox>` shows allowed and blocked requests.
- The Bash tool collapses every `\\` in a command to `\`, and a project hook blocks such commands. Write files with
  backslashes with the file-write tool, or use PowerShell.

## Questions

Each question ends with exactly one status: **Answered**, **Partial** (gap stated) or **Blocked** (reason stated).
Evidence is a command with its relevant output, or a quote with its source. Never print a secret value. For
`GH_TOKEN`, print only its length and whether it starts with `ghp_` or `github_pat_`.

### Q1. What does `sbx` do with a `github` service secret? (no token needed)
- Method: quote `sbx secret --help`, `sbx secret set --help`, `sbx policy ls` and anything in `sbx policy inspect`
  about GitHub. Fetch at most 2 pages of the Docker Sandboxes docs about secrets or credentials. In the Q2 sandbox,
  record `GH_TOKEN`'s length and prefix as above.
- Answered when the results say: which hosts the token is injected for, as which header; whether storing it widens
  egress by itself; whether `GH_TOKEN` is a placeholder; and whether git gets a credential helper. Each point has a
  source, or is marked unknown.

### Q2. Which hosts do the GitHub operations need? (no token needed)
- Method:
  1. Profile `s8-anon`: `network.allow = ["github.com", "api.github.com"]`, no secrets. Clone `https://github.com/tutros/sbxm`
     into `E:\sbxm-it\spike-s8\projects\spike-s8-anon` on the host, then `sbxm new spike-s8-anon --profile s8-anon`.
  2. In the sandbox, from the workspace: `git ls-remote origin HEAD`, `git fetch origin`,
     `gh issue view 1 -R tutros/sbxm --json title`, `gh api repos/tutros/sbxm --jq .full_name`. Record the output and
     exit code of each.
  3. `sbx policy log sbxm-spike-s8-anon-claude`: list every GitHub-related host that was allowed or blocked.
- Answered when every command has output and exit code, and the results list the hosts each one needed. A `401` from
  `gh` with the placeholder token is a valid result.

### Q3. Do push, PR and issue edits work through the proxy? (needs the precondition)
- Method, in project `spike-s8-auth` (profile `s8-auth`: the hosts from Q2, `secrets.services = ["github"]`), a
  clone of `<owner>/sbxm-spike-s8`:
  1. `gh api user --jq .login`, and `GH_TOKEN`'s length and prefix.
  2. `git switch -c spike-s8-branch`, commit a file `spike-s8.txt`, then `git push -u origin spike-s8-branch`. If git
     asks for credentials or fails, retry once with `gh auth setup-git` first, and record both attempts.
  3. `gh pr create -R <owner>/sbxm-spike-s8 --head spike-s8-branch --title "spike S8" --body "Fixes #1"`.
  4. `gh issue comment 1 -R <owner>/sbxm-spike-s8 --body "spike S8 comment"`, and tick a task-list item by editing the
     issue body (`gh issue edit 1 --body-file …`).
  5. The token's value never enters the sandbox: grep `/home/agent`, `/etc` and the workspace for `ghp_` and
     `github_pat_` (count matches only), and `sbx policy log` for the hosts used.
- Answered when steps 1–5 have output and exit codes, with the exact git setup that made push work, or Partial if
  only some steps did.

### Q4. Do the limits hold? (needs the precondition)
- Method, in the same sandbox:
  1. `git push origin HEAD:main` (a direct push to the protected branch): expect a refusal and quote it.
  2. `gh pr merge <pr> --merge -R <owner>/sbxm-spike-s8`: expect a refusal (review required) and quote it.
  3. Commit `.github/workflows/spike-s8.yml` (a no-op workflow) to `spike-s8-branch` and push: expect a refusal because
     the token has no Workflows permission, and quote it.
  4. `gh repo view tutros/sbxm --json viewerPermission`: expect `READ` or an error, since the token has no access there.
  5. `curl -sS -o /dev/null -w "%{http_code}" https://uploads.github.com/`: expect the proxy to block it (a host not
     in the allowlist).
- Answered when all 5 have output, each marked held or not held.

## Budget (hard limits)

- At most **60 tool calls** and **45 minutes**. **No model calls** (no `claude`, only shell commands via `sbx exec`).
- At most **2 sandboxes**, named `sbxm-spike-s8-*`, with `[resources] cpus = 2`, `memory = "2g"`.
- At most **2 web fetches**, only `docs.docker.com` pages about sandboxes.
- When a limit is reached: stop, clean up, write the results with what you have.

## Stop rules

- The same error twice in a row for the same step: record it as Blocked and move on.
- Never run `sbx secret set|rm`, `sbx login|logout`, `sbx settings set`, `sbx policy allow|deny|rm|reset`,
  `sbx reset`, `sbx prune`, `gh auth login|logout|refresh`, or anything interactive.
- GitHub writes only to `<owner>/sbxm-spike-s8`. Never write to `tutros/sbxm` or any other repo; Q2 only reads.
- Never print secret values, `~/.config/gh/hosts.yml` or `/proc/*/environ`.
- Write only under `E:\sbxm-it\spike-s8\` and to `sdlc/spikes/S8-results.md`. No changes to the sbxm repo's code, docs or
  git state.
- New questions go under "Follow-ups" in the results, uninvestigated.

## Cleanup (always, including after failure)

1. `SBXM_CONFIG_DIR=E:\sbxm-it\spike-s8\config sbxm rm <project> --purge --yes` for each `spike-s8-*` project, then
   `sbx rm -f` any `sbxm-spike-s8-*` sandbox still listed.
2. Remove `E:\sbxm-it\spike-s8\`.
3. Leave the scratch repo, its PR and the stored `github` secret alone. The results tell the human to delete the
   repo, revoke the token and run `sbx secret rm github`.
4. Paste into the results: `sbx ls` has no `sbxm-spike-s8-*`; `sbx secret ls` matches the start; `E:\sbxm-it\spike-s8`
   doesn't exist.
