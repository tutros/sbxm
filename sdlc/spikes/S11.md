# Spike S11: can sbx templates replace `setup.install` and stop the egress creep?

Started 2026-10-02 on `sbx` 0.46.0 (Windows host), from the worktree `H:\sbxm-spike-s11` on branch `spike-templates`.
Question: can `sbx template save` and `sbx create -t TAG` replace the per-sandbox `setup.install` work (about 2.5
minutes per sandbox) and let a sandbox's allow list shrink to what an agent needs, instead of every profile listing
the build hosts (`cdn.pyke.io`, `sh.rustup.rs`, `static.rust-lang.org`, `crates.io`, the apt mirrors)?

**Verdict: not answered, and the spike stopped early for a reason that matters on its own.** Of the 8 questions, **0
were tested with a template** (no template was saved, no sandbox was created). The disk on `C:`, where Docker keeps
its sandbox disks, was at 7.2 GB when the spike began and reached **0 GB** at about 16:50, while the one sandbox running on
the machine (a worker building `fastembed`, issue #63) was compiling. The safety rule for this spike (never create a
sandbox with under 10 GB free; wait at most 10 minutes) therefore ended it. What follows is what was verified
read-only, what the `sbx` help and the existing code imply (marked **implied**, not tested), and the exact procedure
to finish the spike once the disk has room. Nothing here is a decision.

## What was verified

**V1. The flags exist together on one command.** `sbx create --help` (0.46.0) lists `-t, --template string`
("Container image to use for the sandbox (default: agent-specific image)"), `--pull always|missing|never`, and
`--kit` ("additional kit reference, must be a mixin; Experimental") as flags of the same `sbx create`. `sbx template
save SANDBOX TAG [--output FILE]` stores the image in the sandbox runtime's image store and the help says to reuse it
with `sbx run --pull never -t TAG AGENT [WORKSPACE]`. Whether `-t` and `--kit` *behave* well together is not tested.
`sbxm` builds its create call in `src/backend/sbx.rs` (`create_args`): `create --name N --cpus C -m M --skills S
--kit <common> --kit <harness-h> <agent> <workspace>`, so a template would add `-t TAG --pull never` and nothing else.

**V2. A "template" is the sandbox's base image.** `sbx template ls` lists the built-in agent images
(`docker.io/docker/sandbox-templates:claude-code-docker`, `codex-docker`, `gemini-docker`, `shell-docker`, plus
`sbx/antigravity-image`, `sbx/pi-image`) beside saved templates; `-t` replaces "the agent-specific image". So a saved
template would take the place of `claude-code-docker` under the kits, which agrees with the kit layering sbxm uses.

**V3. Template metadata is thin.** `sbx template ls --json` returns per image: `id`, `repository`, `tag`, `flavor`,
`created_at`, `size` (bytes). Sizes of the built-in ones: `claude-code-docker` 0.94 GB, `codex-docker` 1.35 GB,
`gemini-docker` 0.77 GB, `shell-docker` 0.60 GB. There are **no labels, no source sandbox and no free-form
description** locally. `sbx template inspect` refuses local images ("requires --cloud in v1; local templates are
docker images; inspect them with Docker"), and this host has no `docker` CLI. So sbxm cannot store its config hash
*in* a template; the hash has to live in the tag (`sbxm-<profile>-<harness>:<hash12>`) and in a record sbxm keeps
itself, like it already does for sandboxes (`state.json`).

**V4. What the install steps cost today.** From the `sbxm task` logs of the PR 57 review runs: apt (C toolchain) 41.9
s, rustup 13.0 s, PowerShell 6.1 s, Pester 6.0 s, `cargo install just` 84.2 s: **about 151 s of `setup.install` per
sandbox**, run again for every worker, reviewer and fix sandbox. This is the baseline a template would have to beat;
the from-template time was not measured.

**V5. Where the allow list and the install steps live.** `sbxm config show --profile sbxm-dev --harness claude
--kits` shows both in the `common` mixin kit (`permissions.network.allow`, `environment.variables` including
`SBXM_CONFIG_HASH`, and `setup.install`); the `harness-<h>` kit only has `requires.agent`. `src/kit.rs` copies the
profile's allow list verbatim (`allow: profile.network.allow.clone()`) and adds **no** provider hosts: the agents'
own API hosts come from the agent, not from sbxm's kit. So every host in `sbxm-dev`'s allow list exists for installs
or builds, and a "baked" kit variant (same file without `setup.install`, with a smaller allow list) is a small
change in one function.

**V6. What a sandbox costs on disk, and where it goes.** The running worker's sandbox owns three sparse images under
`%LOCALAPPDATA%\DockerSandboxes\sandboxes\state\sandboxd\containerd\root\`: `...erofs\snapshots\315\rwlayer.img`
**20 GB** (logical), `...volume.driver.v1.block\images\sbxm-task-issue-63-claude-docker.img` **10 GB**, and the
agent-plugin image **2 GB**. Logical sizes are the ceilings; what is really allocated grows as the sandbox writes.
Measured: `C:` free went 6.4 GB (16:42) -> 5.4 (16:47) -> 3.8 (16:48) -> 0.1 (16:49) -> 0 (16:50) while the worker
was building (a debug build of `fastembed` and ONNX Runtime, about 156 crates, with `CARGO_TARGET_DIR=/tmp/target`
inside the sandbox's own disk). **The big disk consumer is the build output, not the install steps**, so a template
cannot fix the disk problem by itself. After `C:` filled, `sbx ls` answered `try: sbx login`, i.e. the daemon
degraded; I did not touch it.

## Implied by the above, not tested

- **Egress.** With every install baked into the template, the runtime kit would need no build hosts for an
  unchanged repo: `cargo --version`, `rustc`, `just` come from the image, and `cargo build --offline` works **if** the
  template pre-warmed `~/.cargo/registry` with `cargo fetch --locked` of the repo's `Cargo.lock`. That is exactly the
  part that was not tested (whether `--offline` finds everything, what the warm cache adds to the template size, how a
  `Cargo.lock` change fails).
- **The creep is only partly removed.** A task that *adds a dependency* (the cosine issue adds `fastembed`, which
  needs `index.crates.io`, `static.crates.io` and `cdn.pyke.io`) needs those hosts whatever the template holds. A
  template removes the hosts that exist only for the toolchain (`sh.rustup.rs`, `static.rust-lang.org`, apt,
  `packages.microsoft.com`, the PowerShell Gallery); it does not remove the registry hosts for tasks that change the
  lock file. Per-task egress (workflow note G1) is still needed for those.
- **Two hashes, not one.** `sbxm`'s config hash covers install steps *and* the allow list. A template made from the
  wide profile and a sandbox run with the narrow runtime kit have different effective configs, so sbxm needs a
  *template hash* (profile + harness + install steps + pins, what the image contains) and the existing *runtime
  hash* (what the sandbox was created with). `open` refusing on drift would compare the runtime hash only; a profile
  change that touches installs marks the template stale.
- **Stale templates.** A sandbox created from an old template keeps working (an image layer it already uses); only
  new creations pick up a rebuilt template. Unverified whether `sbx template rm` refuses while a sandbox uses the
  image.

## What to run to finish the spike (needs about 20 GB free on C:)

Run when `sbx ls` shows nothing else running and `(Get-PSDrive C).Free` is at least 20 GB (a from-scratch sandbox,
its template and one from-template sandbox exist at once). Names start with `sbxm-spike-tpl`; take `sbx ls`, `sbx
secret ls --json` and `sbx template ls` before and after.

1. `sbxm new spike-tpl-build --harness claude --profile sbxm-dev` (time it; note `C:` free before and after).
   Optionally `sbx exec ... cargo fetch --locked` in the repo's workspace to warm the registry.
2. `sbx stop sbxm-spike-tpl-build-claude`, then `sbx template save sbxm-spike-tpl-build-claude
   sbxm-spike:sbxm-dev-claude-test` (time it; `sbx template ls --json` for the size; if `save` wants a running
   sandbox, record that).
3. Write a variant kit (copy `sbxm config show --kits` output; delete `setup.install`; set `permissions.network.allow:
   []`), then `sbx create --name sbxm-spike-tpl-from -t sbxm-spike:sbxm-dev-claude-test --pull never --kit <variant>
   claude <workspace>` (time it). Does `sbx create` accept `-t` with `--kit`? Do the install steps run again if the
   original kit is passed?
4. In `sbxm-spike-tpl-from`: `cargo --version`, `rustc --version`, `just --version`; `curl -sS -m 10
   https://static.rust-lang.org` and `https://crates.io` (expect blocked); `cargo test --offline` in a copy of this
   repo's `Cargo.lock` (warm vs cold registry); edit `Cargo.lock` and rebuild to see the failure message.
5. Secrets: search the from-template sandbox for the anthropic placeholder-resolving data as S4 and S9 did, and run a
   one-line headless claude command to prove the service secret still works.
6. Disk: `Get-ChildItem $env:LOCALAPPDATA\DockerSandboxes -Recurse -File | Sort Length -Desc | Select -First 6` after
   step 1 and after step 3; compare the sandbox images and whether the template's layers are shared.
7. Clean up: `sbx rm` only the two `sbxm-spike-tpl-*` sandboxes, `sbx template rm` only the test tag, diff the
   three snapshots.

## Recommended design (to confirm with the run above before deciding)

- `sbxm template build <profile> [--harness h]`: create a build sandbox with the full profile (installs and wide
  allow list), optionally warm the registry from the current repo's lock file (`--warm <path>`), stop it,
  `sbx template save` it as `sbxm-<profile>-<harness>:<templatehash12>`, remove the build sandbox, record the tag,
  template hash, `sbx` version, size and date in a file sbxm owns (`<config dir>/templates.json`).
- `sbxm template ls|rm`: from that file plus `sbx template ls --json`; flag a record whose image is gone.
- `new`, `open --rebuild` and `sbxm task` use a template when one exists for their profile, harness and template
  hash (`-t TAG --pull never` plus the **baked** kit: the same `common` mixin without `setup.install` and with the
  profile's `[network] runtime_allow` instead of `allow`); without one they fall back to today's behavior, so
  nothing breaks for people who never build a template.
- Profile gets two lists: `allow` (what the template build needs) and `runtime_allow` (what a sandbox from the
  template needs; empty for an unchanged repo). A task that adds dependencies still names its own extra hosts
  (G1).
- Doctor: warn when a template's `created_at` is older than a month or its template hash no longer matches the
  profile, and when the drive holding Docker's sandbox state has under 10 GB free (it is where this spike died).

## Risks and unverified

1. Everything about `save` and `-t` behavior (the list above). The design could fail at "install steps run again
   whenever a kit is given", which would make the baked kit the only way and add the variant work.
2. Disk. If templates share no layers with sandboxes, each template adds its full size (the built-in agent images are
   0.6-1.3 GB; with Rust, PowerShell and a warm registry expect several GB) on the drive that already ran out.
3. `sbx template` local `inspect` needs the `docker` CLI, which is not installed here: sbxm must not depend on it.
4. Template build time is the same 2.5 minutes, paid once per profile change instead of once per sandbox; but a
   template for each (profile, harness) pair multiplies disk.
5. A template pins the image of the agent as it was when saved; agent updates (`claude-code-docker` is re-published
   every few days) are not picked up until the template is rebuilt, which may be a feature or a trap.

## Proposed decision (unnumbered; the main session numbers it after the run above)

Do not adopt templates yet. Finish spike S11 on a machine state with at least 20 GB free on the sandbox drive. If
`-t` combines with `--kit` and the offline build works, adopt `sbxm template build|ls|rm`, a template hash separate
from the runtime hash, a baked kit variant, and `runtime_allow` in profiles, as an opt-in that falls back to the
current install-on-create behavior. Independently of templates, make `sbxm doctor` check the free space of the drive
that holds Docker's sandbox state, and give tasks a way to name extra egress hosts per task.

## Workflow notes

- **The spike could not run because another job filled the disk.** There is no way to ask "is there room for a
  sandbox?" before creating one, and no reservation: two sandboxes started in this session (a worker and the
  spike) are enough to exhaust a 10 GB-free drive. `sbxm doctor`/`new` should check the sandbox drive and refuse
  under a threshold (workflow note G8), and a `just disk` recipe could print free space per drive plus the largest
  files under `%LOCALAPPDATA%\DockerSandboxes`.
- **A full disk degrades `sbx` into "try: sbx login"**, which looks like an auth problem. `sbxm doctor` should say
  "the sandbox drive is full" before it reports anything about login.
- **Worker disk use is dominated by build output inside the sandbox**; a `[sandbox] disk_budget`, or putting
  `CARGO_TARGET_DIR` on a size-limited volume, would stop one worker from taking the drive.
- **Concurrent heavy jobs need a gate.** The "up to 3 sessions" rule counts sessions, not disk; a script that
  checks free space before a spike or a second worker (`just can-start`) would enforce what the rule intends.
- **`sbx template inspect` is cloud-only**, so there is no scriptable way to read what a local template contains;
  record what sbxm needs in sbxm's own file.
- **Spike procedure** (baseline snapshots, create throwaway, probe, search, clean up, diff) is the same script
  candidate as S9's `scripts/spike-sandbox.ps1`, plus a disk-free precondition.
