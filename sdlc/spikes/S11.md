# Spike S11: can sbx templates replace `setup.install` and stop the egress creep?

Two runs, both on `sbx` 0.46.0 (Windows host). The first (2026-10-02, branch `spike-templates`) stopped before it
created a sandbox, because the drive that holds Docker's sandbox disks filled up. The second (2026-10-11, branch
`spike-s11-finish`, issue #200) ran the whole procedure with sbxm binary `4730ace` and the `claude` harness.
Question: can `sbx template save` and `sbx create -t TAG` replace the per-sandbox `setup.install` work and let a
sandbox's allow list shrink to what an agent needs, instead of every profile listing the build hosts (`cdn.pyke.io`,
`sh.rustup.rs`, `static.rust-lang.org`, `crates.io`, the apt mirrors)?

**Verdict: yes, it works. 8 of 8 questions were tested.** A sandbox created from a saved template takes about 7 s
instead of about 68 s. It has the Rust toolchain, the C toolchain, the crate registry and the ONNX Runtime cache.
With a kit that has no install steps and an **empty allow list**, `cargo clippy`, the test build and the test run
of this repo worked with every build host blocked. The `anthropic` service secret still works and no real secret
value was found in the template. A template costs 1.3 to 2.6 GB on the sandbox drive, once, and the sandboxes
created from it share that layer. The gain is smaller than it looked on 2026-10-02, because the profile no longer
installs PowerShell, Pester or `just` (decision 183): the install steps are now about 56 s, not 151 s.

Nothing here is a decision. Everything below is observed unless it is marked **inferred**.

## Conditions of the second run

- Profile: a copy of `profiles/sbxm-dev` as on `main` (apt and rustup only; config hash `2a9974ee6210`). Resources:
  4 CPUs, 8 GB. Harness: `claude` only. Other harnesses were not tested.
- Every timing was taken with **no other sandbox running** (`sbx ls` checked before each one). One sandbox of another
  session existed but was stopped the whole time. Timings are wall clock of the whole command, measured on the host.
- Sandbox workspaces were on `H:`; Docker's sandbox disks are on `C:`, which had 21.7 GB free at the start and never
  went under 12.8 GB.
- The repo copy used for builds was a plain copy of the repo at an earlier `main` (no `.git`, no `target`).
- The three templates:
  - **T0**: tools only (apt packages and Rust 1.93.0).
  - **T1**: T0 plus the crate registry, warmed with `cargo fetch --locked` (209 crate files, 434 MB).
  - **T2**: T1 plus the ONNX Runtime cache (`~/.cache/ort.pyke.io`, 101 MB) and a build folder that holds the
    compiled dependencies only (`/tmp/target` after `cargo test --no-run`, `cargo clippy --all-targets` and
    `cargo clean -p sbxm`: 611 MB).

- The reported size includes the base image. A template adds **one layer** on top of the base image's layers, so the
  base layers are shared with every other sandbox.
- **Template layers are shared with the sandboxes created from them.** A from-template sandbox started at 0.31 GB
  of its own; a from-scratch sandbox with the same content had 1.49 GB of its own. So from the second sandbox on, a
  template saves disk (about 1.2 GB per sandbox for T1).
- A sandbox's writable disk file does not shrink when files are deleted inside the sandbox (`cargo clean` freed
  4.6 GB inside, the file on the host stayed at 6.3 GB). The space came back when the sandbox was removed.
- `C:` free space, in order: 21.7 GB at the start; 20.0 after the first sandbox; 18.2 after T1; 13.6 after the cold
  test build in the build sandbox; 12.8 after T2 (lowest point); 19.5 with only T2 left; 21.5 after cleanup.
- V6 still holds: **the build output, not the installs, is what fills the drive.** A template does not change that.

## Egress and builds

All in from-template sandboxes with the narrow kit (no install steps, empty allow list).

- **Registry only (T1) is not enough for this repo.** `cargo build --offline --locked` compiled 94 crates and then
  failed: `ort-sys failed to download prebuilt binaries from https://cdn.pyke.io/... : http status: 403`. The
  `fastembed`/`ort-sys` dependency downloads ONNX Runtime in its build script.
- **The ONNX Runtime cache covers it.** After one real build, the download is in `~/.cache/ort.pyke.io` (101 MB).
  With that folder in the template (T2) and a cold build folder, `cargo build --offline --locked` finished in 36 s
  with no network. So `cdn.pyke.io` does not have to stay allowed, as long as the template was built with one real
  build of the repo and the `ort-sys` version is unchanged.
- **`--offline` is not needed when the lock file is unchanged.** Plain `cargo clippy --all-targets`, `cargo test
  --no-run` and `cargo test --no-fail-fast` (the gate commands as they are today) ran in the T2 sandbox with the
  empty allow list: cargo did not contact the index. Test result: 1486 passed, 1 failed. The failing test
  (`the_generated_table_matches_the_spec_on_a_crlf_checkout`, "git checkout-index failed") needs a git checkout and
  the workspace was a plain copy; the same test was not run in a from-scratch sandbox, so that cause is **inferred**.
- **The compiled dependencies are reused across workspaces.** The template's build folder was made in the workspace
  `.../spike-tpl-build`; in a sandbox with the workspace `.../spike-tpl-warm` cargo recompiled only `sbxm` itself (1
  crate instead of 171).
- **A new dependency fails clearly.** With `left-pad` added to `Cargo.toml`: `cargo build --offline` (with or
  without `--locked`) says `error: no matching package named 'left-pad' found ... you're using offline mode`.
  Without `--offline` it says `failed to get successful HTTP response from https://index.crates.io/config.json ...
  got 403` with the body `Approval required for index.crates.io:443. Review and respond with: sbx policy approval
  ls`. So a task that changes dependencies still needs the registry hosts (workflow note G1).
- **A blocked install step can pass silently.** A kit that kept the install steps but had an empty allow list
  still created the sandbox with both steps marked done: the rustup step took 90 ms. Its form is `curl ... | sh`,
  so when `curl` gets a 403 the step's exit code is the empty `sh`'s. The same would hide a failed download in a
  from-scratch sandbox. This is a property of the profile's command, not of templates.
- The Claude kit's own startup command (`apt-get update`, run on every start) tries `security.ubuntu.com` and
  `download.docker.com` and is blocked; the sandbox starts anyway.

## Secrets

Method as in S4 and S9: look for presence only, print counts, names and lengths, never a value.

- In a T1 sandbox: 0 matches for the Anthropic key pattern in the environment, in process command lines, in process
  environments and in a search of the whole filesystem (without `/proc`, `/sys`, `/dev`, `/run` and the workspace).
- The template does hold `~/.claude/.credentials.json` (256 bytes, written when the build sandbox was created). Its
  two token fields are 26 characters long and are **placeholders** that the proxy swaps, not real tokens. A real
  token would have matched the search above.
- The template also holds `~/.claude.json` with a `userID` and a `machineID` (identifiers, not secrets), and
  everything else the build sandbox had in its home folder. **Inferred:** if an agent had run in the build sandbox,
  its sessions and transcripts under `~/.claude` would be in the template too. Here no agent ran before a save.
- `sbx secret ls` (names only) was the same before and after: `google`, `anthropic`, `openai`, no custom secrets.

## What was verified in the first run (2026-10-02), still valid

**V1. The flags exist together on one command.** `sbx create --help` (0.46.0) lists `-t, --template string`
("Container image to use for the sandbox (default: agent-specific image)"), `--pull always|missing|never`, and
`--kit` ("additional kit reference, must be a mixin; Experimental") as flags of the same `sbx create`. `sbx template
save SANDBOX TAG [--output FILE]` stores the image in the sandbox runtime's image store and the help says to reuse it
with `sbx run --pull never -t TAG AGENT [WORKSPACE]`. `sbxm` builds its create call in `src/backend/sbx.rs`
(`create_args`): `create --name N --cpus C -m M --skills S --kit <common> --kit <harness-h> <agent> <workspace>`, so
a template adds `-t TAG --pull never` and nothing else. The second run used exactly that form.

**V2. A "template" is the sandbox's base image.** `sbx template ls` lists the built-in agent images
(`docker.io/docker/sandbox-templates:claude-code-docker`, `codex-docker`, and so on) beside saved templates; `-t`
replaces "the agent-specific image". A saved template shows the `flavor` of the agent it was saved from
(`claude-code-docker`) and the repository `docker.io/library/<name>`.

**V3. Template metadata is thin.** `sbx template ls --json` returns per image: `id`, `repository`, `tag`, `flavor`,
`created_at`, `size` (bytes). There are **no labels, no source sandbox and no free-form description** locally. `sbx
template inspect` refuses local images ("requires --cloud in v1; local templates are docker images; inspect them
with Docker"), and this host has no `docker` CLI. So sbxm cannot store its config hash *in* a template; the hash has
to live in the tag and in a record sbxm keeps itself, like it already does for sandboxes (`state.json`).

**V4. What the install steps cost.** On 2026-10-02: apt 41.9 s, rustup 13.0 s, PowerShell 6.1 s, Pester 6.0 s,
`cargo install just` 84.2 s, about 151 s per sandbox. Since decision 183 only apt and rustup are left: 55.7 s and
58.9 s in the two from-scratch creations of the second run.

**V5. Where the allow list and the install steps live.** Both are in the `common` mixin kit
(`permissions.network.allow`, `environment.variables` including `SBXM_CONFIG_HASH`, and `setup.install`); the
`harness-<h>` kit only has `requires.agent`. `src/kit.rs` copies the profile's allow list verbatim and adds **no**
provider hosts: the agents' own API hosts come from the agent, not from sbxm's kit (seen again in the second run:
`api.anthropic.com` and `platform.claude.com` were allowed with an empty kit allow list). So every host in
`sbxm-dev`'s allow list exists for installs or builds, and a "baked" kit variant (same file without `setup.install`,
with a smaller allow list) is a small change in one function.

**V6. What a sandbox costs on disk, and where it goes.** A sandbox owns sparse images under
`%LOCALAPPDATA%\DockerSandboxes\sandboxes\state\sandboxd\containerd\root\`: a writable layer (`rwlayer.img`, 20 GB
logical), a 10 GB volume image and a 2 GB agent-plugin image. Logical sizes are ceilings; what is allocated grows as
the sandbox writes. On 2026-10-02 a worker's build took the drive from 6.4 GB free to 0 in 8 minutes. After `C:`
filled, `sbx ls` answered `try: sbx login`.

## Recommended design (not a decision)

- `sbxm template build <profile> [--harness h] [--warm <repo path>]`: create a build sandbox with the full profile
  (installs and the wide allow list); with `--warm`, run `cargo fetch --locked` and one real build of the repo so
  the registry, the ONNX Runtime cache and the compiled dependencies exist, then drop the repo's own build output
  (`cargo clean -p <crate>`); stop it; `sbx template save`; remove the build sandbox; record the tag, the template
  hash, the `sbx` version, the size and the date in a file sbxm owns. No agent runs in a build sandbox.
- Tag: `sbxm-<profile>-<harness>:<templatehash12>`. The hash is in the tag because the image has no place for it
  (V3). A new hash is a new tag, so an old template is never replaced under a running sandbox by accident; `save`
  onto an existing tag would replace it without asking (question 8).
- `sbxm template ls|rm`: from sbxm's file plus `sbx template ls --json`; flag a record whose image is gone. `rm`
  should refuse while one of sbxm's sandboxes records that template, because `sbx` does not refuse.
- `new`, `open --rebuild`, `sbxm task` and `sbxm run` use a template when one exists for their profile, harness and
  template hash: `-t TAG --pull never` plus the **baked** kit (the same `common` mixin without `setup.install` and
  with a runtime allow list instead of the build allow list). Without a template they fall back to today's
  behavior. The baked kit matters for egress, not for time: the original kit on a template costs only about 4 s more.
- Profile gets two lists: the build allow list (what the template build needs) and a runtime allow list (what a
  sandbox from the template needs; empty for this repo with an unchanged lock file). A task that adds dependencies
  still names its own extra hosts (G1).
- Two hashes: a template hash (profile, harness, install steps, and for a warm template the lock file) and the
  existing runtime hash. `sbx ls --json` does not show a sandbox's image, so sbxm records the template tag in its
  own `state.json` / `task.json`.
- `doctor`: warn when a template record's image is gone, when its hash no longer matches the profile, and when the
  drive holding Docker's sandbox state is short of space.

## Risks and limits

1. **The gain is modest now.** About 61 s per sandbox, so 2 to 5 minutes per task with 2 to 5 sandboxes. The warm
   dependencies add about 38 s per sandbox on the first gate run. Before decision 183 the gain would have been about
   2.5 minutes per sandbox.
2. **A warm template is tied to the lock file.** After a `Cargo.lock` change the registry is incomplete: the build
   fails clearly (see above) unless the sandbox has the registry hosts. A template with tools only (T0) has no such
   tie, but then the allow list cannot shrink below the registry hosts and `cdn.pyke.io`.
3. **The whole build folder is too big to bake.** 5.2 GB, and 3.7 GB of it is rebuilt anyway because the workspace
   path differs. Only the dependencies (0.6 GB) are worth baking.
4. **Disk.** 1.3 to 2.6 GB per template, per (profile, harness) pair, on the drive that already ran out once. Old
   templates must be removed by sbxm, or they pile up.
5. **A template pins the agent.** The template holds Claude Code as it was when saved (2.1.280 here). **Inferred:**
   updates of `claude-code-docker` are not picked up until the template is rebuilt.
6. **What the build sandbox's home folder holds goes into the template** (placeholder credentials file, user and
   machine identifiers; see "Secrets"). A template exported with `--output` and shared would carry those. Not tested:
   `--output` and `sbx template load`.
7. **Only `claude` was tested.** That `codex`, `antigravity` and `pi` behave the same is **inferred**. Pi and
   Antigravity are kits of their own (`agent_arg` is a kit reference), so `-t` with them needs its own check.
8. **Timings are without contention.** With two or three sandboxes compiling at once the absolute numbers are
   higher; whether the saving grows or shrinks was not measured.
9. `sbx template` local `inspect` needs the `docker` CLI, which is not installed here: sbxm must not depend on it.
10. `--kit` and templates are both marked experimental or thinly documented in `sbx` 0.46.0; pin the minimum
    version and keep a real-`sbx` test.

## Recommendation

**Adopt with limits.** Templates do what was hoped: creation drops from 68 s to 7 s, the allow list of a sandbox
for an unchanged repo can be empty, secrets keep working, and disk use per sandbox goes down. The limits: build it
as an opt-in that falls back to install-on-create; bake the tools, the registry, the ONNX Runtime cache and the
compiled dependencies, not the whole build folder; keep per-task egress (G1) for tasks that change dependencies;
let sbxm own the template records and their removal. Whether about a minute per sandbox is worth a milestone now is
for the user to decide; the stronger argument is the empty allow list, not the time.

## Workflow notes

- **A disk check before a sandbox is created is still missing** (workflow note G8). This run checked
  `(Get-PSDrive C).Free` by hand before every creation and every save.
- **A full disk degrades `sbx` into "try: sbx login"** (first run), which looks like an auth problem.
- **Worker disk use is dominated by build output inside the sandbox**: 5.2 GB for one test build of this repo, in
  a disk file that does not shrink until the sandbox is removed.
- **Install steps of the form `curl ... | sh` hide a failed download** (see "Egress and builds").
- **`sbx template inspect` is cloud-only**, so there is no scriptable way to read what a local template contains;
  record what sbxm needs in sbxm's own file.
- **`sbx exec` has no `sbxm` counterpart** (S9 said the same): every probe went through `sbx exec ... bash -lc`.
  A login shell is needed for `cargo` to be on `PATH`.
- **Spike procedure** (baseline snapshots, create throwaway, probe, search, clean up, diff) is the same script
  candidate as S9's `scripts/spike-sandbox.ps1`, plus a disk-free precondition. The helper scripts and logs of this
  run are outside the repo (`H:\sbxm-e2e\s11-*`).
