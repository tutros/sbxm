# Spike S9: how does the Jev token reach the Jev call?

Run 2026-10-02 on `sbx` 0.46.0 (Windows host), from the worktree `H:\sbxm-spike-s9` on branch `spike-s9`. Question (from
`sdlc/milestone-2.md`): decision 36 keeps secret values in `sbx`, so a host-side `reqwest` client has no token source.
Can `sbx secret set-custom` (a placeholder env var, swapped by the proxy on requests to a named host) carry the Jev
token from a throwaway evaluator sandbox instead, with the value never readable on sbxm's host side or in a sandbox?

**Verdict: yes.** It works, with a fake token, against a header-echo host (`httpbin.org`, plus `postman-echo.com`
for the "other host" case). The proxy swaps the placeholder for the real value in request **headers** to the named
host only. `sbx secret set-custom` is marked EXPERIMENTAL in its own help, so pin the minimum `sbx` version and keep a
real-`sbx` test.

All values below are fake (`S9-...`); no Jev token was used. The user's real secrets (`google` stored, `anthropic` and
`openai` OAuth) were listed before and after and are unchanged; no `rm --all` was ever run.

## Setup used

```
sbx secret set-custom --host httpbin.org --env JEV_API_KEY --value S9-FAKE-TOKEN-7f3a91c2
  Saved custom secret placeholder "sbx-cs-FAKE-PLACEHOLDER-ONE" for target "httpbin.org" env "JEV_API_KEY" in scope "(global)"
sbxm new s9-spike --harness claude --profile default     # SBXM_CONFIG_DIR=H:\sbxm-e2e\config
```

The egress allowance came from a project override written **before** `sbxm new`
(`<base>/.sbxm/s9-spike/sandbox.toml`: `[network] allow = ["httpbin.org"]`); sbxm has no flag for that (see Workflow notes).

## Recommended design for the Jev evaluator

1. **The call runs from a throwaway evaluator sandbox that runs a fixed command, not an agent** (decision 120 rejected
   an agent layer; a scorer reachable from a contestant's sandbox breaks decision 112). sbxm writes the request
   JSON into the evaluator's workspace, the sandbox runs `curl --fail -sS -X POST https://api.typesafe.ai/v1/systemone
   -H "Authorization: Bearer $JEV_API_KEY" -H "Content-Type: application/json" --data @request.json -o response.json`
   under the in-sandbox `timeout`, and sbxm reads `response.json` back with the same link-free, size-capped reader it
   uses for agent files (`repo::read_agent_file`'s checks). The token is only ever a header, which is what the swap supports.
2. **Secret naming and scope: a secret scoped to the evaluator sandbox, created before the sandbox.** sbxm picks the
   sandbox name (`sbxm-run-<id>-jev`), creates `sbx secret set-custom --sandbox <name> --host api.typesafe.ai
   --env JEV_API_KEY --placeholder sbxm-jev-<run-id> --command <token_command>`, creates the sandbox, runs the call,
   removes the sandbox, then removes the secret by `--placeholder ... --sandbox ...`. A scoped secret keeps the
   placeholder out of every contestant's sandbox (a global one would put it in all of them).
3. **Where the real value comes from:** `[eval.jev] token_command = "<absolute path>"` (a helper outside any workspace and
   outside the temp dir, as `sbx` requires) or `token_ref = "op://..."`, never `--value`, never an env var of sbxm's
   own. Config names the source; the value is never in config, results or errors. No `token_env` exception to
   decision 36 is needed.
4. **Egress of the evaluator sandbox:** `api.typesafe.ai` only, from a built-in evaluator profile, not the contestant's.
5. **Preflight (before any write):** `[eval.jev]` present means `sbx --version` supports `set-custom`, `token_command`
   exists and runs (`set-custom` verifies `--command` unless `--no-verify`, so sbxm can let it), and no leftover secret
   with that env name and host exists in global scope (it would make `sbx create` fail with the 400 above; refuse and say
   how to remove it).
6. **Fallback if the secret lifecycle proves fragile:** a global secret stored once by the user
   (`sbx secret set-custom --host api.typesafe.ai --env JEV_API_KEY --placeholder sbxm-jev --command <helper>`), checked in
   preflight through `custom_secrets` (match env and host), with the caveat that every new sandbox carries the placeholder
   and only egress stops a contestant from using it.

Open items for slice 14, not settled here: the real Jev endpoint and header (the docs say Bearer auth to
`POST https://api.typesafe.ai/v1/systemone`; verify with a real token before relying on it), whether the proxy swap applies
to HTTPS requests Jev's server redirects, and a real-`sbx` test that creates and removes the scoped secret (the set-custom
command is experimental).

## Proposed decision (the main session numbers it)

**Spike S9 (run 2026-10-02 on `sbx` 0.46.0): the Jev token reaches its call through `sbx secret set-custom`, in a throwaway
evaluator sandbox, with a secret scoped to that sandbox.** Verified with a fake token: the proxy swaps a placeholder for the
real value in request headers to the secret's host only (not in a body or query, not for another host); the real value is
not in the sandbox's env, process list, `/proc` or filesystem, nor in the proxy log; a scoped secret can be created before its
sandbox and sets the placeholder env var in it. So the host-side `token_env` fallback (an exception to decision 36) is not
needed: the Jev evaluator (slice 14) runs a fixed `curl` in an evaluator sandbox whose egress is `api.typesafe.ai` only, with
`sbx secret set-custom --sandbox <name> --host api.typesafe.ai --env JEV_API_KEY --placeholder sbxm-jev-<run-id> --command
<token_command>`; the token source is named in config (`token_command` or `token_ref`) and never passed with `--value`. Cautions:
`set-custom` is experimental in `sbx`; a global and a scoped secret with the same env and host make `sbx create` fail
(`400 invalid custom secrets`); `sbx secret ls` masks a `--value` secret to its first 8 and last 4 characters.

## Workflow notes: what sbxm can't do yet, and where a script or command could define the process

Each of these was hit during this spike.

1. **Custom secrets can't be expressed in config or checked by preflight.** `secrets.services` names global *service* secrets
   only, and preflight/`doctor` look only at `secrets[]`. A `[[secrets.custom]]` entry (host, env, placeholder, source) with a
   check against `custom_secrets` is the missing piece; slice 14 needs it for Jev and any later tool would too.
2. **No way to create a throwaway sandbox with one extra egress host.** I wrote `<base>/.sbxm/<project>/sandbox.toml` by hand
   before `sbxm new`. A `sbxm new --allow-host <h>` flag, or a `just scratch <name> <host>` recipe (create, print the
   name, clean up on exit), would define the process.
3. **`sbxm rm --purge` doesn't remove secrets scoped to the sandbox.** They are orphaned (`sbx secret rm --placeholder X
   --sandbox N -f`). `sbxm list`/`doctor` should flag orphan custom secrets the way they flag orphan sandboxes, and
   `rm` should remove what sbxm created.
4. **Removing a custom secret is easy to get wrong.** The positional argument is a service name, custom secrets need
   `--placeholder` plus the right `--sandbox`, and `--all` removes every secret including the real ones. A small script
   (`scripts/secrets-snapshot.ps1`: list, diff against a saved baseline, refuse `--all`) would make "prove the real
   secrets are untouched" a command instead of a habit.
5. **No `sbxm exec`.** Every probe went through `sbx exec`, which prints "Sandbox ... started successfully" on stdout
   (noise when parsing). A thin `sbxm exec <project> --harness h -- <cmd>` would also make evaluator-style fixed
   commands a first-class operation.
6. **The spike procedure itself is a script waiting to be written:** baseline the secrets, set a fake one, create a sandbox,
   run the probe commands, search the sandbox for the value, clean up, diff the baseline. `scripts/spike-sandbox.ps1` (or a
   `just spike` recipe) taking the probe commands as input would make a spike repeatable and its evidence uniform.
7. **Masking on the host:** `sbx secret ls` shows 12 characters of a `--value` secret. The README's secrets section should
   tell users to store tokens with `--command`/`--ref`.
