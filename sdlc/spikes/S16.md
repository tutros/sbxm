# Spike S16: Google OAuth for Antigravity sandboxes through a proxy placeholder

Issue #288. Run 2026-10-29, 16:19-19:50 UTC, hands-on in the main session, `sbx` v0.46.0 (`991967dc`), kit
`docker.io/sbx/antigravity-kit:20260928-7da9425e…` (sbxm's pin, decision 104), `agy` 1.4.10, Windows host.
Everything is observed unless marked **inferred**. No token value was printed, pasted or written to the repo: the
user signed in and copied the token file out by hand, and only field names, lengths and HTTP status codes were looked
at.

**Verdict:** route A works. A sandbox that holds only placeholder tokens runs a headless prompt, with `sbx`'s proxy
swapping in an access token that a host helper refreshes; the refresh token never enters a sandbox. Three conditions
come with it: the secret must cover two hosts, the helper must be fast and cache the token itself, and the MCP gateway
entry (#287) must be removed before every run.

## How it ran (7 steps)

1. Sandbox `sbxm-s16-agy` created with the pinned kit on a throwaway workspace.
2. The user signed in by hand (`sbx run`, Google OAuth). Baseline: headless `pong`, `SUCCESS`, 3.3 s in `agy`, 6 s
   with `sbx exec`.
3. The user copied `~/.gemini/antigravity-cli/antigravity-oauth-token` to a host folder outside every mount.
4. Q1 in a second sandbox, `sbxm-s16-q1`.
5. Q2 from `agy`'s logs and `sbx policy log`.
6. Q3 with a host refresh helper.
7. Both sandboxes, the scoped secret and the host folder removed; `sbx secret ls` showed nothing left.

## Q1: does `agy` send a placeholder token unchanged? PASS

The second sandbox got a token file with placeholder values (`access_token`, `refresh_token`), `expiry`
`2099-01-01T00:00:00Z`, `auth_method: consumer` and a fake `id_token_email`. A custom secret scoped to the sandbox:

```
sbx secret set-custom --sandbox sbxm-s16-q1 --host daily-cloudcode-pa.googleapis.com --host www.googleapis.com \
  --env S16_AGY_TOKEN --placeholder <placeholder> --command <absolute host helper>
```

- With `daily-cloudcode-pa.googleapis.com` alone, the eligibility check passed but `agy` then failed with `failed to
  fetch user info: 401`: it calls `https://www.googleapis.com/oauth2/v2/userinfo` with the same bearer token. Adding
  `www.googleapis.com` fixed it: `pong`, `SUCCESS`, 14 s in `agy`.
- The first attempt failed with a 401 for a different reason: the copied access token had expired (Google access
  tokens live one hour), so the helper must refresh (Q3).
- `sbx policy log` shows the two secret hosts as `forward` (the proxy reads the request) and the kit's other Google
  hosts as `forward-bypass` (passed through unread). Adding a secret for a host turned it from `forward-bypass` into
  `forward`.

## Q2: does `agy` refresh or validate the token itself? PASS (no)

- Neither `agy`'s logs nor `sbx policy log` show any call to `oauth2.googleapis.com` or to `oauth2/v3/tokeninfo`
  (the binary has that URL, with the token in the query string, where the proxy would not swap it; it was never
  called in these runs).
- The sandbox's token file was unchanged after every run, and no `ya29.` string (a real access token's prefix) was
  anywhere under `~/.gemini`.
- `aicode.googleapis.com` (3 calls) and `play.googleapis.com` (telemetry, 8 calls, HTTP 401) went `forward-bypass`,
  so they only ever saw the placeholder. `pong` did not need them; a feature that does would fail (**inferred**).
- The log lines `You are not logged into Antigravity` appear in the really signed-in sandbox too: they are not caused
  by the placeholder.
- In a really signed-in sandbox `agy` refreshes an expired token on its own (seen: a run after expiry wrote a new
  `expiry`). With a far-future placeholder `expiry` it never tries.

## Q3: what does the host helper need? Answered

- `agy`'s binary holds three OAuth client ids (`*.apps.googleusercontent.com`) and three `GOCSPX-` client secrets.
  One pair (the first id with the second secret) refreshes the user's token (HTTP 200); another pair gave 401. They
  are `agy`'s own installed-app credentials; they were kept in a host-only file and are not recorded here.
- The refresh is a plain `POST https://oauth2.googleapis.com/token` with `grant_type=refresh_token`. A helper doing
  it, with the pair above, made `pong` pass (`SUCCESS`, 13.6 s in `agy`).
- **`sbx` runs the helper for every proxied request:** about 30 calls, one a second, during one `pong` (`refresh:
  on-demand` in `sbx secret ls`). So the helper must cache the access token (it refreshed once and served the cache
  after), and it must start fast: a PowerShell helper took about 0.9 s a call, which made `pong` 38-41 s end to end
  against 6 s for the signed-in sandbox.
- `sbx secret set-custom` runs the helper once to verify it; a failing helper is refused (`verify command failed`).

## Q4: is it stable across `agy` updates? No guarantee

The same kit tag gave `agy` 1.2.13 (2026-09), 1.4.5 (2026-10-22) and 1.4.10 now: `agy` updates itself, so the pin
does not fix its version. The route depends on four things an update could change: the token file's path and fields,
the hosts that take the bearer token, `agy` not validating the token, and the client pair. A `real_sbx` check of a
placeholder `pong` would catch a break.

## #287 (MCP gateway hang), seen again

The gateway entry in `~/.gemini/config/mcp_config.json` is written when the sandbox is created, again on `sbx run`,
and again whenever a stopped sandbox starts (an `sbx exec` on a stopped sandbox restarts it). A run with the entry
back hung until the 120 s timeout (`MCP: 1 server(s) still connecting`). Emptying the file in the same `sbx exec`
command as `agy` worked every time. So a kit file alone won't hold; the file has to be emptied right before each run.

## What it means for sbxm

The user adopted route A on 2026-10-29 (decision 270). The build is issue #330, size L, with five open points to
