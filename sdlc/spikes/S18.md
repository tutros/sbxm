# Spike S18: can sbx sandboxes use MCP servers through sbx's gateway today?

Issue #332, its "to decide" point 1. Run 2026-11-02, about 19:00-19:20 UTC, hands-on in the main session, `sbx`
v0.46.0 (`991967dc`), local sandboxes only, Windows host. Claude Code 2.1.306 in the built-in `claude` image.
Everything is observed unless marked **inferred**.

**Verdict:** the two harnesses tested, the default Claude Code and Codex setups, both fail to use the gateway, by
different routes. `sbx`'s MCP gateway serves registered servers correctly to a raw client, but it never answers an MCP
notification; Claude Code, which waits for that reply, times out (**inferred** that the unanswered notification is the
cause). Codex fails separately: it ignores the gateway's `headers`/`type` config keys and never sends the bearer
header, so it was not tested against the notification at all. Antigravity was not re-run; #287's hang is plausibly the
same gateway fault (**inferred**: the same gateway and the same "still connecting" symptom, not observed here). A
second finding matters more now: Claude Code in every sbxm sandbox connects to the signed-in account's **claude.ai
connectors**
(Gmail among them) through Anthropic's MCP proxy, which the egress allow list does not stop.

## How it ran (6 steps)

1. Registered a no-auth public server: `sbx mcp add deepwiki --url https://mcp.deepwiki.com/mcp` (status `ready`,
   gateway `LOCAL, managed by you`).
2. `sbx create claude <ws> --name spike-mcp-claude --static-mcp deepwiki`; read the harness config and probed the
   gateway with `curl` from inside.
3. `claude mcp list` and a headless `claude -p` asking for a deepwiki tool.
4. `sbx create codex <ws> --name spike-mcp-codex` (no `--static-mcp`), the same probe, then `sbx mcp load deepwiki
   --sandbox spike-mcp-codex`, `codex mcp list` and a `codex exec` asking for the tool.
5. `sbxm new spike-mcp` (binary `eabaebd`, the `default` profile of the test config) to check the connectors in an
   sbxm sandbox, and its egress.
6. Removed both `sbx` sandboxes, the sbxm project (`rm --purge --yes`) and the `deepwiki` registration; `sbx ls`
   shows nothing left.

## What sbx offers and how a server is chosen

- **Registration is per host user:** `sbx mcp add <name>` with `--url` (a remote endpoint, an MCP registry URL, a
  `server.json` manifest URL or a `dhi.io` image) or `--command` (a stdio process that **runs on the host** with the
  user's full rights; `sbx`'s own help calls it "for ad-hoc development only"). OAuth servers are authorized with
  `sbx mcp auth`; header secrets go in `sbx secret set mcp:<server>:<placeholder>` and never enter the sandbox.
- **Choice is per sandbox:** `sbx create/run --static-mcp a,b` fixes the set at creation; `sbx mcp load <name>
  --sandbox <s>` adds one to a running sandbox. A cloud sandbox resolves names on the cloud gateway (`--cloud`).
- **One endpoint in the sandbox:** every harness's config points at `http://mcp-gateway.docker.internal/mcp` with
  `Authorization: Bearer proxy-managed` (`MCP_GATEWAY_URL` is set). The image writes that entry itself, even with no
  `--static-mcp` (S6b saw the same for Codex and Gemini).
- The gateway adds two tools of its own next to a server's: `code-mode` and `mcp-exec`.

## The gateway works for a raw client

From inside `spike-mcp-claude`, `curl`:

| Request | Result |
|---|---|
| `initialize` (POST) | `200`, SSE, an `Mcp-Session-Id`, deepwiki's instructions |
| `tools/list` (POST, same session) | `200` in 0.04 s: `ask_wiki_question`, `read_wiki_contents`, `read_wiki_structure`, `code-mode`, `mcp-exec` |
| `notifications/initialized` (POST, Accept JSON and SSE) | **no answer**: 0 bytes after 15 s (the spec wants `202 Accepted` at once) |
| the same with `Accept: application/json` only | `400` in 0.02 s |
| GET (the server's SSE stream) | `200`, stream held open (expected) |

The same five rows in `spike-mcp-codex` with **no** server registered for it: the notification hangs there too, so the
hang is the gateway's, not deepwiki's.

## Claude Code: fails to connect

`claude mcp list`: `mcp-gateway ... ✘ Failed to connect — MCP server "mcp-gateway" connection timed out after
30000ms`. The headless prompt answered that the tool's server "didn't connect in this session (it timed out after 30
seconds)". **Inferred:** Claude Code's client waits for the notification's reply, which never comes.

## Codex: ignores the gateway's config

Even with deepwiki loaded live (`MCP server "deepwiki" loaded into sandbox "spike-mcp-codex" (live)`), `codex exec`
warned `mcp_servers.mcp-gateway.headers is ignored` and `mcp_servers.mcp-gateway.type is ignored`, and answered "I
can't access the mcp-gateway `read_wiki_structure` tool in this session". `codex mcp list` shows the entry `enabled`
with auth `Unsupported`. The image writes keys this Codex no longer reads, so the bearer header is never sent.

## Finding: claude.ai connectors bypass the egress allow list

In a plain `sbx` sandbox and in an sbxm sandbox (`sbxm new`, `default` profile), `claude mcp list` shows the account's
claude.ai connectors next to the gateway:

```
claude.ai Claude Docs: https://api.anthropic.com/v1/pages/mcp - ✔ Connected
claude.ai Gmail: https://gmailmcp.googleapis.com/mcp/v1 - ✔ Connected
```

From that sbxm sandbox, `curl https://gmailmcp.googleapis.com/mcp/v1` gets `403` (the proxy blocks the host), while
`https://mcp-proxy.anthropic.com/` gets `404` (reached). So the connectors travel through Anthropic's MCP proxy on an
allowed host, and a worker, reviewer or contestant could read or act on the account's connected services whatever the
profile allows. `ENABLE_CLAUDEAI_MCP_SERVERS=false` in the environment removes them (`claude mcp list` then shows only
the gateway). sbxm doesn't set it today (`grep` of `src/` and `profiles/`). Not checked: a strict template sandbox
(`sbxm-dev` refused to start without a warmed `Cargo.lock`), and whether a connector's tool call succeeds, not only
its connection.

## What it means for #332

- Point 1 is answered: neither tested harness can use the gateway on `sbx` v0.46.0 (Claude Code times out on the
  unanswered notification; Codex ignores the config keys), and Antigravity is untested. MCP support in sbxm waits for
  a fixed gateway (and, for Codex, an image that writes keys Codex reads), or goes around the gateway with per-harness config
  (point 2's second option), which then needs each server's hosts on the allow list and its secrets as `sbx` secrets.
- Host `--command` servers run outside every sandbox with the user's rights, a route from a sandbox back into the host,
  which decision 80 rules out because it would undo the isolation of decision 40: sbxm should accept only `--url` servers.
- The connector finding stands on its own and is its own issue, #381: sbxm should set `ENABLE_CLAUDEAI_MCP_SERVERS=false`
  in every Claude sandbox it makes, unless a profile opts in.
