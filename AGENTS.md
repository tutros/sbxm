## Workflow

The repo is `tutros/sbxm` on GitHub (public since 2026-09-27, `MIT OR Apache-2.0`; `origin`, branch `main`). Code review findings are GitHub issues there (decision 79); close them from fix commits with `Fixes #n`. Every change, docs and planning files included, goes to a branch and a PR after an initial code review, and the independent reviewer runs on the PR before the user merges: for a PR `sbxm task finish` opened, that is the in-task review it posts while the PR's head is the reviewed commit, and `sbxm task review --pr N` for any later commit and every other PR; never push to `main` (decisions 86, 187). A low-risk PR (the reviewer's level and the path-rule floor) whose latest review covered its head commit with 0 must-fix is merged by GitHub's auto-merge without the user (decision 266, an experiment of 10 PRs; medium and high risk stay the user's). A PR made in the session, not by a worker, first goes
through the self-review in `sdlc-implementation` ("Before reporting a change done"), and a commit pushed after a PR's
last review gets a narrow re-review or is named in the PR as unreviewed (decision 251, an experiment for the next three
hand-made PRs).


Each SDLC phase has a project skill in `.claude/skills/`; follow it for that phase:
- `sdlc-planning`: interview rounds, numbered decisions, spikes, milestone plan.
- `sdlc-implementation`: vertical slices, TDD (red first), smallest change per step, commit after every green step (`cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`). A milestone is built as one batch on one branch (rule 8): a short report per slice, a background review of each risky slice while the next is built (decision 162), one full review at the end.
- `sdlc-code-review`: review a milestone at its end (the normal review), a worktree before merging, or a slice when asked or risky; findings need evidence, fixes go back through TDD.
- `sdlc-retro`: look back over the work since the last retro (numbers per task, patterns with at least two instances, last retro's experiments) and propose at most three process changes as experiments for the user to decide; records in `sdlc/retros/` (decision 196).

## Working rules

- **Show progress as `[current] of [total]` (user rule, 2026-10-01).** Whenever you mention a step that is complete or in progress, give its position and the total: "slice 4 of 13", "test case 3 of 7", "step 2 of 5". This covers milestone slices, test cases within a slice, review rounds, manual steps for the user, and any other sub-step whose total is known. If the total isn't known yet, say so rather than leaving it out.
- **Say when work can run in parallel, up to 3 sessions in total (user rule, 2026-10-01).** Whenever upcoming work has parts that don't depend on each other (independent slices, a background review next to the next slice, a research spike, docs next to code), say so and name each part as its own session, counting the current one: at most 3 at once. Say which parts must wait and why (shared files, one part's output feeding the other). Don't start extra sessions without the user's go-ahead.
- **No open questions go to a worker (user rule, 2026-10-11, issue #206).** Before `sbxm task start` or `task run`, answer every "to decide when building" point of the issue or spec with the user, one at a time with a recommendation, and write the answers into the issue or spec. A worker in a sandbox can't ask, so an open point becomes a guess that the review then argues about. Ask one more question there (decision 244): does the change have a limit, a size, or an identity (path, drive, ref) that decides behavior? If yes, the issue lists the boundary cases (at the limit, one over, one under, the largest input) and the worker writes those tests first.
- **Every issue gets a size, twice (user rule, 2026-10-13).** When an issue is created, by hand or from a review finding, give it a `size:S`, `size:M` or `size:L` label and a `**Size:**` line with the reason; the table is in the `sdlc-code-review` skill (section 8, "Size"). When its open points are answered under the rule above, confirm or change the size in the issue and on the label: the scope is only fixed then.

## Code layout

Crate `sbxm` (edition 2024), lib + bin. Modules grow slice by slice, following the crate layout table in `sdlc/milestone-1.md`.
- `src/lib.rs` / `src/main.rs`: everything lives in the lib; `main` parses args and passes `SbxBackend` to commands.
- `src/cli.rs`: `clap` derive definitions. `run_target_order` (decision 193, issue 201) reads `task run`'s raw `ArgMatches` back for the written order of its repeatable `--issue`/`--spec` flags, which clap's derive API doesn't carry for two different repeated flags on its own.
- `src/disk.rs` (issue 210, decision 194): the free-space check of the drive holding `sbx`'s sandbox state. `parse_size` (`min_free_disk`), `platform_state_dir` (Windows only), `state_dir` (`sandbox_state_dir` over the platform default), `describe`/`gib` for messages, and `require`, which every sandbox-creating command calls before any write with a `Guard` (the free-space reader, the default folder and `--ignore-disk`; `Guard::real` in `main`, a fake reader in tests); `doctor` reads the same drive through its `Host` and only warns.
- `src/config.rs`: config dir resolution (`SBXM_CONFIG_DIR` or `~/.config/sbxm`), `GlobalConfig` loading (unknown keys are errors, `default_harness` has its own message; decisions 76, 77; `min_free_disk`, parsed to bytes with a 10 GiB default, and `sandbox_state_dir`, decision 194), and `Profile` loading (unknown keys are errors; env names/values and `skills.store` are checked on load, `SBXM_` env names are reserved), `Profile::with_project` merging `.sbxm/<project>/sandbox.toml` over it (decision 57), plus instruction files (read at load, contents hashed, paths must stay inside the defining file's folder; decision 62), `setup.install` steps, `harness.claude.home_files` (folder read at load, no links, kit-owned files refused; decision 63) and `harness.claude.managed_settings` (a JSON object, stored compact; decision 64), and the config hash per harness (`config_hash`, `GlobalConfig::current_hash`; decisions 55, 69).
- `src/harness.rs`: `Harness` (`claude`, `codex`, `gemini`, `pi`, `antigravity`; a `clap::ValueEnum` for `--harness`, default `claude`): `sbx` agent name and `agent_arg` (for Pi and Antigravity, the Docker Hub kit pinned to a tag, `agent_kit`, which is also part of the config hash; decisions 73, 104), always-loaded instructions file, `unsupported` settings (warned about) and `applied` (the profile without them, which the kit and hash use; decision 69).
- `src/project.rs`: project name validation (decisions 33, 44), sandbox name, metadata dir.
- `src/backend/`: `SandboxBackend` trait (`Send + Sync`; `create`, `list`, `stop`, `remove`, `attach`, `validate_kit`, `secret_services`, `version`, `exec(sandbox, &ExecSpec) -> ExecOutput` with a workdir and `Stdin::Closed | Piped`, and `skills()`), `SbxBackend` (shells out to `sbx`; parsers unit-tested against captured output in `src/backend/fixtures/`), `FakeBackend` (records calls, plus an ordered `log()`; `failing_create()`, `failing_remove()`, `with_sandboxes()`, `with_invalid_kit()`, `with_secrets()`, chainable `and_sandboxes()`, `with_version()`, `without_sbx()`, `failing_list()`).
- `src/headless.rs`: the shared headless-execution primitive (M2a slice 1, decisions 94, 114): `run(backend, sandbox, workdir, harness, prompt, opts, timeout)` wraps the harness's command in `timeout -v --kill-after=10 <secs>` inside the sandbox, calls `SandboxBackend::exec` and returns a `HeadlessResult` (`Completed`/`TimedOut`/`Failed`, answer, raw transcript, usage); a timeout is recognised by `timeout -v`'s stderr line, not by exit code alone. An `Err` from `exec` itself (never a failing agent command, which is `Ok` with a status) is wrapped as `ExecUnavailable`, carrying the same "`sbx` couldn't run" meaning as `task::pipeline::SbxUnavailable`, so `sbxm task run`'s list orchestration can still recognize it as a queue-wide stop once `task_start.rs`'s own multi-issue failure aggregation would otherwise have erased the type (issue 201 review M-2, repeat of M-2). Claude, Codex and Antigravity have adapters (`Harness::headless_argv`/`stdin`/`git_repo_workaround`/`budget_flag`/`parse_headless_output`; Codex gets an empty piped stdin and `--skip-git-repo-check` outside a git repo); fixtures of real output in `src/fixtures/`.
- `src/run/`: `sbxm run` (M2a). `config.rs`: `RunConfig::load` parses and validates a run-config (every struct denies unknown keys; contestant count 2-4, `repeat`, harness allowlist claude/codex/antigravity for contestants and judge, rubric/check ids, scale levels, weights, durations `90s`/`10m`/`2h`, `[eval.cosine]`'s optional `model_dir` resolved like `task.seed`, `Cosine::resolve_model_dir` filling in the default once a config dir is known; errors are one line naming the file; decisions 107, 109, 125, 166). `preflight.rs`: `check` adds what needs the host and `sbx`, all before any write: seed dir (same checks as `new --seed`), the cosine model's five files existing under its resolved `model_dir` (named first-missing-file, folder, URL; decision 166), profile loading (run, contestant and judge profiles), the deduplicated secret union (provider per `Harness::provider_secret`, judge, every profile's `secrets.services`) and the warnings (budget flag missing, `Harness::unsupported` per contestant and judge). `kits.rs`: `build` writes and validates the run's kits (`common` + `harness-<h>` per (profile, harness) pair used by a contestant or the judge, hashed with the run's `cpus`/`memory` overrides) under a caller-given root before any sandbox exists; a contestant's own `profile` or else the run's decides which (decision 133), and `get_for(profile, harness)` finds a set. `id.rs`: run IDs (`<date>-<6 hex>`) and the atomic reservation of a run's two roots, `<base>/.sbxm/runs/<id>/` and `<base>/runs/<id>/`. `orchestrate.rs`: `execute` runs the pairs (parallel per repeat via `std::thread::scope`, repeats as sequential waves), seeding each pair's workspace when the run has a seed, creating and removing one sandbox per pair, capturing the pair's diff, and returns `PairOutcome`s; `in_sandbox_path` maps a host path to its mount (`E:\x` is `/e/x`). `diff.rs`: `seeded` (`git add -A` + `git diff --cached <baseline>` against a host-owned git dir) and `unseeded` (`git diff --no-index` of an empty folder against a link-free, `.git`-free copy). `src/git.rs` is the only place host `git` runs on a contestant's workspace: hardened (own `--git-dir`, no global/system config, no inherited `GIT_*`) because a contestant can plant a `.git/config` that runs commands (decision 127); `seed::seed_contestant` makes the one-commit baseline in both repos. `results.rs`: what a run leaves under `<base>/.sbxm/runs/<id>/` (decision 128): `run.json` (identity, written before any sandbox; `completed_at` only once every pair saved), a verbatim `run-config.toml`, and per pair `<contestant>/<repeat>/{answer.md,diff.patch,transcript.jsonl,result.json}` written by `execute_with`'s per-pair callback the moment the pair finishes (`result.json` last). `checks.rs`: `run_checks` runs the `[[eval.checks]]` in a pair's sandbox (`sh -c` under the in-sandbox `timeout`, pass = exit 0, `hit_timeout` shared with `headless`) after the diff and before removal; the prompt goes in `judge-prompt.md` in the judge's workspace, not on the command line (decision 131). `score.rs`: `rank` (weight-normalised mean over the judged criteria, repeats averaged, unscored excluded, ties rank equal, checks alongside), `load` (ranks a saved run from `run-config.toml` plus each pair's `result.json`/`evals.json`) and `render`; The Bash tool here turns every `\\` in a command into `\` before bash runs it: in heredocs, single quotes and scripts alike (a lone `\` is unaffected; the PowerShell tool keeps backslashes intact). A `PreToolUse` hook (`.claude/hooks/block-double-backslash.py`, registered in `.claude/settings.json`) blocks any Bash command containing `\\`. Write files that need backslashes (JSON fixtures, Windows paths, Rust `\n` escapes inside strings) with the Write/Edit tools, or use PowerShell. Exception: the Write/Edit tools decode a JSON-style unicode escape (backslash, `u`, four hex digits) into its character, so write those with PowerShell (`[char]92`) or build them in code (`char::from(92)`).

## What `sbxm` is

A Rust CLI (crate/binary name `sbxm`) that wraps Docker Sandboxes (`sbx`) to:

1. **Milestone 1: sandbox lifecycle.** Create or reuse a sandbox for a project at `<base_dir>/<project>`, applying a shared, versioned common config (egress allowlist, secret references, instructions file, per-harness hooks/guardrails). Commands: `new`/`open`, `list`, `stop`, `rm`, `config show`, `config profiles-dir`, `doctor`.
2. **Milestone 2: comparisons.** Run 2–4 *contestants* (`harness × model × optional config profile`) headless and in parallel on the same task, each in a fresh snapshot of an optional seed directory. Capture answer, diff and transcript, then evaluate with any subset of executable checks, rubric-based LLM judge, Jev (TypeSafe System One), cosine similarity (text answers only) and human review.

## Architectural constraints (from sdlc/decisions.md)

- **sbxm enforces nothing itself:** `sbx` handles egress (deny-by-default proxy), secrets (proxy-injected placeholders) and isolation. sbxm compiles config into **schemaVersion "2" mixin kits** (one shared plus one per harness pinned with `requires.agent`) and passes them to `sbx create --kit`. `sbx ls --json` doesn't expose kits or env, so sbxm keeps its own host-side state. See "Spike results" in `sdlc/decisions.md` for verified `sbx` behavior.
- **Mandatory instructions** go in each harness's always-loaded user-level file via the per-harness mixin's `files/home/`. Kit `agentInstructions` is only surfaced on demand, so it's for reference material only.
- **Timeouts must be enforced inside the sandbox** (`sbx exec … timeout --kill-after=… <limit> <cmd>`). Killing `sbx exec` on the host leaves the agent process running.
- **Base dir must not be on `C:`:** on this Windows machine `sbx` fails to mount any workspace on `C:` (not only `%TEMP%`/AppData; decision 56). Use `E:`.
- **`SandboxBackend` trait:** all `sbx` interaction goes through it (shelling out to the `sbx` CLI). A `bollard` backend may be added later, and tests use a fake backend by default.
- **Harness adapters:** each harness (Claude Code, Codex, Gemini CLI, Pi) gets an adapter that owns its headless command, transcript/usage parsing, native config file names (`CLAUDE.md`/`AGENTS.md`/`GEMINI.md`, hooks), and provider egress domains. If a configured feature is unsupported, warn loudly; never drop it silently.
- **Config:** TOML layered global (`~/.config/sbxm/config.toml`) → named profile → project `sandbox.toml`. Record a hash of the merged config with every sandbox and run. A changed hash on an existing sandbox requires `--rebuild`.
- **Security is a core goal:** egress is deny-by-default. Config only *names* secrets (values live in `sbx secrets`), and secret values must never reach results files. Seed directories are copied into a fresh git repo with a single baseline commit (no history or remotes). Project names are restricted to `[a-z0-9-]`, and reserved Windows names are rejected. `rm` deletes project directories only with `--purge` plus confirmation.
- **Evals:** rubric criteria are structured (`id`, `kind` = `pass_fail` | `scale` with levels, `weight`, `notes`) so Jev, the LLM judge and humans score the same criteria. Jev-specific questions are a separate extension point. Contestants are scored independently by default and ranked in code, with blind A/B/C labels for judges and humans.
- **Jev:** HTTP API only (no Rust SDK), called by a fixed `curl` command inside a restricted evaluator sandbox, never by a host HTTP client, so the token stays in `sbx`'s scoped secret (decision 241). 32k-token limit on state plus longest question, so it never receives transcripts, and large diffs are split per file. Docs: https://docs.typesafe.ai/llms.txt. The `typesafe@typesafe-ai` Claude Code plugin (skill `/typesafe:typesafe-ai`) is installed for reference.
- **Results:** plain files under `<base>/<project>/runs/<run-id>/<contestant>/` are the source of truth. `--repeat N` is part of the run model. Timed-out runs keep their partial output and are still evaluated.

## Environment Notes

- Primary platform is Windows (PowerShell) with Docker Desktop. Keep path handling cross-platform (`std::path`, no hard-coded separators).
- Sandbox names are `sbxm-<project>-<harness>`. sbxm metadata lives in `<base>/.sbxm/<project>/`, never inside the mounted workspace.
